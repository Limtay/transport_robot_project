## 30초 요약

```bash
cd orin_ws
./build.sh          # 전 패키지 (의존 순서대로)
./setup_rt.sh       # 최초 1회 — 포트 권한 + latency_timer
./web.sh            # 브라우저에서 http://localhost:8080
```

**웹이 브리지를 띄운다.** 터미널에서 브리지를 먼저 올리면 웹이 기동을 거부한다
(고아 프로세스를 조작하면 누가 그것을 내릴 책임인지가 사라진다). 터미널만 쓰려면
`./run.sh` 로 직접 띄우고 `./cli.sh` 로 조작한다 — 둘을 동시에 올리지 않는다.

## 두 갈래 — 웹과 CLI 는 같은 것을 한다

| | 웹 (`./web.sh`) | CLI (`./cli.sh`) |
|---|---|---|
| 브리지 기동 | 브라우저 패널에서 | `./run.sh` 로 따로 |
| 실시간 조작 | Tab1 슬라이더 | `stream` |
| 프로파일 실험 | Tab2 (세그먼트 편집 → 재생) | `run <yaml> --record` |
| 레지스터 직접 판독 | Tab3 | `command set auto ... raw_read` |
| 기록 | 같은 `record.py` | 같은 `record.py` |

**기록 모듈이 하나**라서 웹으로 돌린 런과 CLI 로 돌린 런은 같은 폴더 규격·같은 토픽의
bag 이 남는다. 분석 파이프라인은 둘을 구분하지 않는다.

## 안전에 관해 먼저 알아야 하는 것 3개

1. **`arm` 없이는 슬라이더·`stream` 이 아무것도 하지 않는다.** STREAM 진입 게이트다
   (01 §6.1.3). 웹의 ④ run 버튼, CLI 의 `arm on` 이 같은 것이다. (프로파일 재생은
   action goal 이라 arm 과 무관하다.) 스트림이 스테일해지면 IDLE 로 내려가고 **arm 도 함께
   꺼진다** — 조작자가 손을 뗀 것을 시스템이 기억하지 않는다.
2. **LOCKED 는 스스로 풀리지 않는다.** ECU 가 명령을 연속 거부하면(0.25초) 브리지가
   래치하고, `rearm` 을 명시적으로 해야 나온다. 원인 확인 없이 실험이 재개되지 않게 하는
   의도된 설계다 → [05_troubleshooting.md](05_troubleshooting.md#locked-가-떴다)
3. **슬라이더에는 레이트 제한이 없다.** 프로파일 재생에는 `slew_rate` 가 있지만 실시간
   조작에는 대응물이 없다. position 모드에서 슬라이더를 빠르게 끌면 모터가 과전류로
   fault 를 내고 그 결과 LOCKED 가 된다 → [02_web.md](02_web.md#3-슬라이더--5-조작)
