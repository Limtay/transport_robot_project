## 2. F1 — "동작 불변" 을 무엇으로 증명하는가

### 2.1 문제 — `colcon test` 만으로는 증명이 안 된다

현재 테스트는 **6파일 42케이스**(2026-07-27 실측)이고, `test/rd_test_fixture.hpp:25` 가
`std::make_shared<orin_bridge::RdBridge>()` 로 **실제 노드를 띄운다.**
그런데 이번 재설계는 그 `RdBridge` 를 4개로 쪼개는 일이다 (A2). 즉 **테스트가 붙어 있는 대상 자체가
사라진다.** 리팩터링 도중에 테스트를 같이 고치게 되고, 그러면 그 테스트는 더 이상 "바뀌지 않았음"
을 증명하지 못한다. 자기가 자기를 검증하는 꼴이 된다.

### 2.2 처방 — 골든 바이트 테스트 (신규, 최우선)

**구조를 어떻게 바꾸든 RS485 와이어로 나가는 바이트열은 같아야 한다.** 그것이 "동작 불변" 의
가장 엄밀한 정의다. 이 성질을 고정한다.

```
test/golden/
  cases.json        # (shadow 상태, SlotDef, auto_mode) → 기대 요청 바이트열 + 기대 파싱 결과
  *.bin             # 실제 캡처한 요청·응답 프레임
```

- 대상: `rd_map` 의 `Encode`/`Decode` (L1). **여기가 wire 계약의 전부다**
- 생성: **재설계 착수 전에** 현행 코드로 만든다. 이것이 0단계다
- 케이스: `auto_mode` 6종 × 프리셋 4종 + REBOOT + 펄스(`SET_ORIGIN`) + OOS WRITE
- 판정: **바이트 단위 완전 일치.** 1비트라도 다르면 실패

이 테스트가 값을 하는 이유:
1. **rclcpp 없이 돈다** (A5 의 `ILogger`/`IClock` 추상화 후 L0/L1 은 순수 C++) → 실기·ROS 불필요
2. 노드를 쪼개도 **검증 대상이 안 사라진다.** `rd_map` 은 L1 이고 분할 대상이 아니다
3. 실패하면 원인이 명확하다 — "구조 개편이 wire 동작을 바꿨다"

> **지금 없다.** 현행 테스트는 상위 동작을 보고 바이트열을 고정하지 않는다. 0단계에서 만든다.

### 2.4 5번 전용 — 인터페이스 인벤토리 테스트

분할 전에 인벤토리를 고정한다.

> 검증량이 적다. **되돌리기도 `git revert` 한 번**이다.

STM 플래시 완료 + ECU RS485 연결, **모터·CAN 미연결** 상태에서 확인한 범위.

| 항목 | 결과 |
|---|---|
| 링크 | ✔ `/dev/ttyUSB0` 115200, `latency_timer=1` |
| **플래시 펌웨어 = 신 레이아웃** | ✔ **확정** (아래 3중 확인) |
| ECU 동작 | ✔ `realtime_tick` 증가 (200ms 에 Δ3473) |
| **P8 게이트** | ✔ **통과** — DIRECT RW 87B ×200, `RD_FATAL` 0 / timeout 0 / decode_err 0 |
| 200Hz 유지 (traction READ) | ✔ ticks 3655, over-period **0/400**, Loss 2(초기 고정) |
| 200Hz 유지 (control RW) | ✔ ticks 3655, over-period **0/400**, avg 2548us |
| `auto_mode` 4/5 write·read-back | ✔ 수용 (4→4, 5→5) |
| `auto_mode` 4/5 **의미** | ⏸ **판정 불가** — 아래 §4.5 |
| cmd_vel 영역 WRITE | ⏸ 전량 `Access Error` — 아래 §4.5 |

**펌웨어 판별을 3중으로 한 이유**: 첫 시도는 `addr32` 비영 비율 1/10 이라 근거가 약했다.
`rs485_proc_delta` 는 `rd_delta_tick` 이 0.1ms 단위라 평시엔 대개 0 이므로 **비영 여부만으로는
구 펌웨어의 `reserved0[0]`(항상 0)와 구분되지 않는다.** 그래서 인과 실험으로 바꿨다.

1. **부하 반응** — 직전 트랜잭션 처리시간이 다음 응답에 실리는 성질(`rd_system.c:643`)을 이용.
   READ 3B 직후 vs RW 87B 직후로 나눠 150쌍 측정:

   | | 비영 비율 |
   |---|---|
   | `addr32` after READ 3B | 26% |
   | `addr32` after RW 87B | **76%** |
   | `addr228` after READ 3B / RW 87B | **0% / 0%** |

   구 펌웨어면 `addr32` 는 `reserved0[0]` 이라 **부하와 무관하게 영원히 0** 이다. 반응 자체가 판별이다.
2. **`hw_reset` 자리** — `rd_system.c:288` 은 CAN fatal 시 `hw.reset.bit.can`(0x08)과 `FAULT` 를
   **함께** 세운다. 실측이 `sys_state=5`(FAULT) 이고 `0x08` 이 **[26]** 에 있다 → [26]=`hw_reset`
   = 신 레이아웃. (구 레이아웃이면 0x08 이 [24] 에 있어야 한다.)
3. **필드 성질** — [24] 가 `0x10`↔`0x12` 로 흔들린다(i2c ↔ i2c|uart2). `hw_error` 는 실시간
   상태라 흔들리고 `hw_reset` 은 래치라 흔들리지 않는다 → [24]=`hw_error` = 신 레이아웃.

**P8 해소가 이번 세션의 핵심 성과다.** 요청이 실제로 87B 인지를 `Encode` 직후 확인해
**재현 조건 성립을 먼저 증명한 뒤** 200회를 돌렸다 — 조건이 안 맞는 통과는 통과가 아니다.
구 RX 64B 에서는 2/2 재현되던 것이 256B 확장 후 200/200 무사고.

### 4.5 모터 미연결이 만든 판정 불가 영역

모터가 없으면 CAN 노드가 없어 **ECU 가 반드시 `SYS_STATE_FAULT` 로 떨어진다** —
`rd_system.c:281~288` 이 `fatal_can1_cnt >= FATAL_MAX` 에서 FAULT 로 보내고, `:393` 이
`if (robot_state == SYS_STATE_FAULT) return;` 으로 **끈끈하게(sticky)** 만든다. 여기서 두 가지가 파생된다.

**(가) cmd_vel 영역 WRITE 전량 거부.** `rd_system.c:634` 의
`mtr_lock = (robot_state != SYS_STATE_AUTO)` 가 1 이 되고, `rd_map_ecu.c:150` 이
addr `132~187` 과 겹치는 WRITE 를 `PACKET_ERR_ACCESS` 로 막는다.
→ 실측과 정확히 일치한다: `cmd_motor 128:52`(겹침) 전량 거부, `auto_mode 188`(비겹침) 정상 통과.
**설계대로 동작한 것이며 버그가 아니다.**

> 이때 브리지 FSM 도 설계대로 반응했다 — 연속 거부 50 tick 에서
> `IDLE → LOCKED (0A 래치)`, `config REARM` 으로만 해제. 01 §6 의 LOCKED 래치가
> 실기에서 처음으로 의도대로 걸린 사례다.

**(나) `auto_mode` 4/5 의 의미는 검증 불가.** `case 4/5` 는 `ACTION_STATE_AUTO()` 안에 있고
이 함수는 `SYS_STATE_AUTO` 에서만 불린다. FAULT 라 **한 번도 실행되지 않았다.**
읽기/쓰기 수용은 확인됐지만 `ctr_mode` 강제는 확인되지 않았다.

> ⚠ **함정**: `auto_mode=4` 에서 `ctr_mode` 가 `3 3 3 3` 으로 읽혀 통과처럼 보였는데,
> `MODE_VELOCITY == 3` 이면서 동시에 `DEF_CTR_MODE == 3`(기본값) 이라 **구분이 안 된다.**
> 실제로 분기가 돌았는지는 `auto_mode=5` → `MODE_POSITION(4)` 로만 알 수 있고,
> 그 값은 `3` 으로 남아 있었다 — 즉 **분기는 돌지 않았다.** 모터 연결 후 재확인 대상.

### 4.11 웹 착수 전 사전 검증에서 나온 결함 2건 (발견·수정 2026-07-28)

ECU 재기동 후 `control_web` 의 조작 흐름(① fb_position ② origin ③④ arm ⑤ 슬라이더 ⑥ arm off)을

#### (가) auto_mode 표시가 셀렉터와 갈라져 있었다 — 커밋 `03ca073`

VELOCITY(4)/POSITION(5) 를 추가할 때(§4.7) 실제 write 범위 셀렉터(`rd_schedule.cpp` 의 4-way
switch)는 갱신됐지만, **여섯 군데에 흩어진 표시용 삼항식** `am == DIRECT ? "DIRECT" : "CURRENT"`
는 그대로 남았다.

```
config auto_mode 5 -> "OK: addr188 = 5 검증 OK / auto_mode=1(CURRENT), write 164:16"
status             -> "auto_mode=5(CURRENT) write=164:16"
```

실제 write 범위는 `132:16` 으로 **옳았다.** 동작은 맞고 보고만 틀렸으므로 조작자가 알아챌
방법이 없다 — 실험 중 어느 단위로 명령이 나가는지 화면만 보고는 판단할 수 없었다.
`ctr_mode` 도 마찬가지로 비-DIRECT 에서 섀도를 전부 CURRENT 로 고정해 두어,
`auto_mode=5` 인데 `ctr_mode=[1,1,1,1]` 로 보고했다.

- **수정**: `ecu::AutoModeName` / `AutoModeWriteSpan` / `AutoModeForcedCtrMode` 를
  `rd_register_ecu.hpp` 에 신설하고 여섯 군데를 대체. 금지 모드의 범위는 `"-"` —
  "없음" 을 `0:0` 으로 위장하지 않는다 (미판독 표현 규약과 같은 이유).
- **보강**: 표시 문자열 ↔ `REG_CMD_*_OFFSET` 교차 검증 테스트 3건.

#### (나) DIRECT 에서 각도가 암페어로 나갔다 — 커밋 `c212ff2` ★

`PrepareWrite` 의 DIRECT 분기가 명령 중이면 `ctr_mode` 를 CURRENT 로 강제하고, 값을
**단위와 무관하게** `cmd_current` 에 꽂았다.

```cpp
const uint8_t mode = cmd_active ? ecu::CTR_MODE_CURRENT : ctr_mode_[i];   // 구 코드
```

도달 가능한 결과가 둘이었다:

| | 증상 | 무게 |
|---|---|---|
| ① | DIRECT + `stream position/velocity` → **경고 없이 버려짐**. FSM 은 STREAM 으로 가고 모터는 안 움직인다 | 조작자가 "arm 이 안 먹었다" 와 구분 불가 |
| ② | DIRECT + `mode: position` 프로파일 → **각도가 암페어로 나간다**. 클램프도 `clamp_prof` 가 아닌 `clamp_a([A])` 라 90도 샘플이 상한(기본 30A)까지 간다 | 위험 |

②가 도달 가능한 이유가 핵심이다. `AcceptsAutoMode` 는 *"DIRECT 에서는 모터별 ctr_mode 가
단위를 정한다"* 고 명시하며 이 조합을 **수락한다**(`rd_profile.cpp:370`). 즉 게이트가 약속한
계약과 실제 write 가 서로 달랐다. 9단계가 `SetProfileLimits` 로 고친 "클램프의 단위
의존"(05 §2.1)이 **DIRECT 분기에만 남아 있던 것**이다.

- **수정**: DIRECT 에서 `ctr_mode_[i]` 를 그대로 쓰고 단위별로 라우팅. `SelectWrite` 의
  STREAM 분기도 DIRECT 면 모터별로 필드를 고른다. IDLE 안전값·펄스는 불변
  (구 코드도 `!cmd_active` 경로는 같았다).
- **보강**: `test_direct_units` 6건. **구 코드에 대고 돌려 3건이 실패하는 것을 확인**했다 —
  버그를 겨눈 3건만 실패하고 비회귀 3건(전류 클램프·IDLE 안전값·SET_ORIGIN 펄스)은
  양쪽 다 통과했다. 테스트가 실제로 그 버그를 잡는지 확인하지 않으면 통과는 의미가 없다.
- **실기**: DIRECT + `ctr_mode=4` + `stream position 30` → 모터 0 → **30.0도 이동**,
  current 0.49A(유지 토크). 수정 전 같은 시퀀스는 무반응이었다.

> **교훈 (반복)**: 게이트가 수락하는 조합과 실행부가 처리하는 조합이 갈라질 수 있다.
> `AcceptsAutoMode` 는 옳았고 `PrepareWrite` 가 그 계약을 안 지켰는데, **양쪽 다 테스트를
> 통과하고 있었다** — 둘을 한 케이스에서 함께 돌리는 테스트가 없었기 때문이다.

### 4.12 `control_web` 완료 (2026-07-28) — 커밋 `7645730`

01 §6.1.3 의 ①~⑥ 만 구현했다. 범위를 넘는 자동화·검증·보정은 넣지 않았다.

**구조**: 브라우저는 setpoint 만 바꾸고 **발행은 노드가 50Hz 로** 한다. 브리지 스테일이
0.1s 라 슬라이더를 가만히 두면 곧바로 IDLE 로 떨어지기 때문이다. 그 대가로 데드맨을 둔다 —
`client_timeout`(기본 1.0s) 동안 브라우저 접촉이 없으면 발행을 멈추고 arm 을 내린다.
탭이 숨으면 `visibilitychange` 로 즉시 stop 한다.

> 데드맨만으로도 결국 멈추기는 한다(크롬이 숨은 탭 타이머를 조인다). 하지만 그건
> **브라우저 throttling 정책에 기대는 것**이고, 멈추는 시점을 우리가 정하지 못한다.

**실기 결과** (DIRECT, M1 `ctr_mode=POSITION`):

| 단계 | 결과 |
|---|---|
| ③ slider=22 | `write=NONE`, 모터 정지 — **안 나간다** |
| ④⑤ run | `STREAM`, fb 0 → **22.00도** |
| ⑥ stop | `IDLE`, **22.00도 유지** (안전값 재시드) |
| 데드맨 | 폴링 중단 2.5초 → `armed=false`. **폴링 재개만으로는 재개 안 됨** (run 필요) |
| 원점 | 회전 중 거부(`fb_velocity=-10 RPM > 5`), 정지 후 38.20 → 2.50도 |

#### 여기서도 조용한 실패가 하나 나왔다 — QoS

발행자를 BEST_EFFORT 로 짰는데 브리지 구독은 RELIABLE 이라, rclpy 가
`"requesting incompatible QoS. No messages will be sent to it"` 만 남기고
**슬라이더가 통째로 안 먹는 상태**가 됐다. 기동 로그에서 잡았다.
증상은 §4.11(나)①과 똑같다 — FSM 은 정상이고 모터만 안 움직인다.

#### 함께 고친 계약 문서 2건

웹이 그대로 믿으면 틀리는 것들이라 웹을 쓰다가 발견했다.

- `ControlFeedback.control_state` 주석에 **STREAM 이 빠져** 있었다
  (`0=INIT 1=IDLE 2=RUNNING 3=LOCKED`). 실제는 `3=STREAM 4=LOCKED` 라,
  주석대로 읽은 소비자는 **STREAM 을 LOCKED 로 오독**한다.
- `CmdMotor.ctr_mode` 는 "DIRECT 에서만 유효" 라고 적혀 있었으나 **브리지가 읽지 않는다.**
  `StreamCmd_t` 에 담기기만 하고 아무도 안 읽는 죽은 필드였다.
  → 예약 필드로 명시하고, 채워 보내면 1회 경고한다.
  **읽게 만들지 않은 이유**: `ctr_mode` 변경은 `OP_SET_CTR_MODE`(IDLE 전용)의 몫인데,
  200Hz 스트림이 그걸 바꿀 수 있으면 회전 중 모드 전환이 가능해져 safe_stop 게이트가
  무의미해진다. 죽어 있던 것이 오히려 안전한 쪽이었다 — 문서만 틀렸다.

#### UI 쪽 규약 위반 하나

`hw_error` 의 255 를 `"err 0xff"` 로 그렸다. 그런데 255 는 에러가 아니라 **미판독
센티넬**이다 — control 프리셋이 `{16,17}` 을 안 읽어 의도적으로 그렇게 나간다
(`rd_telemetry.cpp`: *"0 으로 채워 정상처럼 보이게 두는 것이 훨씬 나쁘다"*).
**"안 읽음" 과 "정상 0" 을 섞지 않으려고 만든 값이 UI 에서 "전 비트 에러" 로 읽혔다.**
→ `"err 미판독"` 으로 표시.

#### 4.13.1 `result.json` schema v2 (05 §5.2, §6.4)

**브리지 쪽 — 없던 값을 만들어낸 것이 절반이다.**

`seed` 가 `LoadFromYaml` 의 **지역변수로만 존재했다.** `seed:` 미지정이면 시각 기반으로
정해지는데, 재생이 끝나면 그 값이 사라져 **noise/prbs 파형을 두 번 다시 만들 수 없었다.**
05 §5.2 가 "기록하지 않으면 영구 소실" 이라고 경고한 그것이 실제로 그 상태였다.
→ `RdProfile::seed_` 로 붙잡고 `Seed()` 로 노출.

`mode`·`irregular_tick_cnt`·`drop_cnt`·`clock_converged`·`drift_ppm` 도 action Result 에
**정의만 있고 전부 0 이었다** (06 F2 가 "값을 채우는 코드는 그 값을 생산하는 단계에 붙는다"
고 미뤄 둔 것). 이번에 채웠다.

- `RunCounters_t` 신설 — L3 가 스냅샷을 주입한다. 종전 `write_err_total` 콜백 하나가
  하던 일을 넓힌 것이고, **L2 가 RdTelemetry 를 직접 참조하지 않는 경계**를 유지한다.
- **카운터는 런 구간의 증분으로 낸다.** 누적을 그대로 실으면 두 번째 런부터 이전 런의
  사고가 섞여 들어와 그 런을 잘못 판정한다.
- `clock_converged` 는 시작·끝 **둘 다** 수렴이어야 true 다. 한쪽이라도 미수렴이면
  그 런의 `header.stamp` 는 등급이 다르다 (05 §5.2 B1).
- `RunProfile.action` 의 `seed` 를 `uint32` → **`uint64`** 로. 시각 기반 시드가 잘린다.

**`verify_run_dir` — 종전에는 파일 존재만 봤다.** `result.json` 이 비어 있어도, bag 폴더만
생기고 rosbag2 가 실패했어도 "규격 충족" 이었다. 05 §6.4 의 4가지를 추가했다:

| # | 검사 | 막는 것 |
|---|---|---|
| ① | v2 필수 키 20개 (값이 null 이어도 키는 있어야) | "없는 것" 과 "안 채운 것" 의 혼동 |
| ② | `schema_version` 이 아는 값인가 | v1 기록 84런과 섞임 |
| ③ | `bag/` 안에 `metadata.yaml` + `*.db3` 실재 | 폴더만 생기고 rosbag2 실패 |
| ④ | **`profile.yaml` sha256 == `result.profile_sha256`** | **기록이 거짓인 채로 통과** |

④가 핵심이다 — "재생된 것과 기록된 것이 같다"(05 §4.3-4)를 런 종료 시점에 실제로
검증하는 유일한 지점이다. CLI 는 불일치 시 **exit 3** 으로 알린다 (경고가 아니다).

**"모른다" 를 0 으로 위장하지 않는다.** 값을 못 받은 필드는 `null` 이다 — `seed=0` 은
유효한 시드이고 `clock_converged=false` 는 "미수렴" 이라는 관측이라, 둘 다 "모른다" 와 다르다.

미구현으로 남긴 것: `slew_exempt_ticks`(E3 자체가 미구현), `missing_tick_cnt`(항상 0).

#### 4.13.2 `SET_READ_PRESET` (04 §2.3, §2.4.2)

종전 응답은 *"미구현 — 프리셋 테이블이 정의된 뒤 (9단계)"* 였다. 그 테이블을 데이터로 만들었다.

- `rd_read_preset.hpp` — `ReadPreset` 구조체 + 표. `RespPayload()` 는 **파생**시킨다
  (04 §2.2.3). 사람이 더해 적으면 프리셋을 추가할 때마다 틀린다 — 04 §2.5 가 지적한
  "43 을 손으로 옮겨 적어 payload 와 wire 를 섞은" 사고가 바로 그것이다.
- 예산은 `static_assert` 가 컴파일 타임에 본다. **예산을 넘는 프리셋은 애초에 고를 수 없다.**
- `(프리셋 × auto_mode)` 조합을 기동 시 전부 만들어 두고 교체는 atomic 인덱스만 바꾼다 —
  200Hz 루프가 읽는 데이터를 건드리지 않는다.
- **id 0 = 현행 배치 그대로.** 기본 동작을 안 바꾼 것이 골든 바이트 테스트 통과로 확인된다.
- id 1 = `diag` — `{16,17}` 을 읽어 **`hw_error`·`degraded_cnt` 가 실값으로 나온다.**
  (§4.12 의 "err 미판독" 이 버그가 아니라 프리셋이 그 구간을 안 읽는 것이었다.)

##### 이 기능의 진짜 어려운 부분은 교체가 아니라 **그 다음**이다

프리셋을 바꾸면 **어떤 섀도 필드는 더 이상 갱신되지 않는다.** 그걸 모르고 발행하면
낡은 값이 신선한 값처럼 나간다 — §4.11·§4.12 와 같은 형태의 결함이 된다.

→ `ITelemetrySink::SetReadPreset()` 통지를 추가하고, 텔레메트리가 매 발행마다
`Covers()` 로 물어 **안 읽는 블록은 미판독 센티넬**(uint8 `0xFF` / float `NaN`)로 낸다.
`fb_position` 이 0 이 아니라 NaN 인 이유: **0 은 "정지" 라는 유효한 관측값**이다.

`Covers()` 는 **부분 포함을 false 로 본다.** 두 세그먼트에 걸친 블록을 "읽었다" 고 하면
그 안의 어떤 필드가 낡았는지 알 수 없기 때문이다.

두 프리셋 모두 `{128,4}`(ctr_mode read-back)를 유지한다 — `SET_CTR_MODE` 검증이 여기에
의존하고, 둘 다 IDLE 전용이라 실제로 겹치는 조합이다. 테스트가 이 불변식을 고정한다.

#### 4.13.3 ECU 실기 확인 — 2026-07-29 **완료 (6/6 통과)**

|---|---|---|

| 2 | `config preset 0` 복귀 | ✅ `fb_position` −41.3 복귀, `hw_error` 다시 255 |

##### ★ 1번이 결함을 하나 잡았다 — `Reads()` 의 널 fallback

첫 시도에서 preset 0 의 `hw_error` 가 **255 가 아니라 0** 으로 나왔다. 원인은 내가 넣은
"안전한 기본값" 이었다:

```cpp
return p ? p->Covers(addr, len) : true;   // 미설정이면 "전부 읽는다"
```

기동 시엔 `SetReadPreset()` 이 한 번도 안 불려 포인터가 널이었고, 그래서 **읽지도 않은
SYS 블록의 낡은 섀도 값 0 이 "정상" 으로 발행됐다.** 실제 값은 16 이었다 — diag 로 바꾸고서야
드러났다. 널일 때 `true` 는 "안 읽는 것까지 읽었다고 주장" 하는 쪽이라, **이 함수가 막으려던
일을 그대로 한다.** 고치기 전보다 나쁜 상태였다.

→ 기본값을 실제 기본 프리셋(`&kPresetControl`)으로 두고, INIT 에서 `sink_->SetReadPreset()`
을 **명시적으로** 부른다 (기본값이 틀렸을 때 조용히 틀린 채로 도는 것을 막는다).
회귀 테스트 `DefaultIsARealPresetNotPermissive` 추가 — 빈 프리셋이 아무것도 덮지 않음을 고정.

> **교훈**: "모르면 관대하게" 가 안전한 기본값이 아닐 때가 있다. 이 함수의 용도가
> **"안 읽었다" 를 말하는 것**이었으므로, 모를 때의 올바른 답은 관대함이 아니라 사실이다.

##### 그 밖에 드러난 것 2건

- **E3(noise 구간 slew 면제) 미구현이 실제로 걸렸다.** `std=0.2A` noise 가
  `slew_rate 53.6 A/s > 50` 으로 거부됐다. noise 는 tick 마다 독립 표본이라 200Hz 에서
  인접 차이가 수백 A/s 로 잡히는 것이 정상이다. 지금은 한계를 열어 두는 것 외에 방법이
  없다 — `slew_exempt_ticks` 와 함께 남은 숙제다.
- **`node_params` 가 `array('q', [1])` 같은 파이썬 repr 로 기록됐다.** `ros2 param get` 의
  사람용 출력을 그대로 넣은 탓이다. 기록은 나중에 읽히는 데이터라 정규화했다
  (실패 시 원문 유지 — 못 읽은 것을 지어내지 않는다).

##### ⚠ 테스트 격리 — 실기 브리지를 띄운 채 `colcon test` 를 돌리지 말 것

`InventoryTest.ControlTopicsAbsentInDefaultMode` 가 실패한다. 코드 회귀가 아니라
**돌고 있는 control 모드 브리지가 같은 ROS 그래프에 있어서** 인벤토리 테스트가 그 토픽을
자기 것으로 보는 것이다. 브리지를 내리면 125/125 통과한다.

### 4.8 ⚠ 되돌려야 하는 임시 변경 — HW ESTOP 우회 (2026-07-28)

**커밋되지 않았고, 워킹트리에만 있다.** 다음 세션에서 제일 먼저 확인할 것.

```c
/* stm_ws/ECU_V3/Core/Src/rd_system.c:414 */
if (/*ECU_PERIPHERAL.data.ESTOP ||*/ECU_PERIPHERAL.data.MODE_DONE) {
        robot_state = SYS_STATE_ESTOP_HW;
```

- **왜 했나**: 물리 ESTOP 스위치를 걸 수 없는 배선 상태라 `sys_state` 가 4(ESTOP_HW)에
  고정돼 AUTO 진입이 불가능했다. 그 상태에서는 write 가 전량 거부되어 §4.5-(가)(나) 를
  검증할 수 없다.
- **왜 `ESTOP` 만 뺐나**: 415 줄 전체를 주석하면 `MODE_DONE` 경로까지 끊긴다.
  :427 의 주석이 *"GPIO 경로는 위 FSM 의 MODE_DONE 이 ESTOP_HW 를 강제하므로 여기서
  중복 발동 없음"* 이라고 **이 줄에 명시적으로 의존**한다. 그 전제가 사라지면 모드 전환
  제동 펄스가 이중 발동하거나 누락된다. 또 if 블록이 비면 ESTOP 이 걸린 동안
  `robot_state` 가 갱신 없이 얼어붙는다(else 로 안 감).
- **남아 있는 안전장치**: 모터 fault 경로(`ESTOP_SW`)는 그대로다 — 과열·과전류·락업·
  활성 모터 피드백 상실은 계속 잡힌다. 끊긴 것은 **물리 스위치 하나뿐**이다.
- **되돌리기**: 위 주석을 원복하고 재플래시. 물리 스위치 복구가 선행되어야 한다.
  되돌리지 않으면 **실차에서 ESTOP 버튼이 동작하지 않는다.**

> 이 우회 상태로 얻은 §4.7 결과는 유효하다 — 우회한 것은 FSM 진입 조건이지 제어 경로가 아니다.
> 다만 **G2 정식 판정은 우회를 되돌린 뒤**에 해야 한다.

## 5. F4 — 롤백 기준

### 5.1 되돌리는 방법

단계 = 커밋 1개이므로 **`git revert <단계 커밋>` 한 번**이다. 그래서 단계 안에서 커밋을 쪼개지
않는다 — 쪼개면 되돌릴 것이 여러 개가 되고, 그 조합이 검증되지 않은 상태가 된다.

### 5.2 트리거 — 판단이 아니라 수치

| 시점 | 조건 | 조치 |
|---|---|---|
| 오프라인 | **골든 바이트 불일치** | **즉시 롤백. 예외 없음** — wire 가 바뀌었다는 뜻이다 |
| 오프라인 | `colcon test` 실패 | 롤백 또는 같은 커밋 내 수정 (아직 안 밀었으면) |
| 오프라인 | 인벤토리 불일치 (5·7번) | 즉시 롤백 |
| 실기 | §4.3 지표 중 **하나라도** 미달 | 롤백 후 원인 분석 |
| 실기 | `RD_FATAL`·재시작 **1회라도** | 즉시 중단. 모터 전원 차단 후 분석 |

**"골든 불일치 = 예외 없음"** 이 이 표에서 제일 중요하다. 골든 테스트가 실패했을 때 기대값을
고치고 싶은 유혹이 반드시 생기는데, 그 순간 이 문서 전체가 무의미해진다. 기대값을 바꾸려면
**"동작을 의도적으로 바꾼다" 는 별도 결정**이어야 하고, 그건 재설계가 아니라 기능 변경이다.

### 5.3 롤백이 아닌 것

- **STM 플래시는 되돌리기 비용이 다르다.** 구 펌웨어 바이너리를 보관하고, G1 실패 시 그것으로
  되돌린다. 소스 revert 만으로는 실기가 돌아오지 않는다
- **`data/rosbags/` 는 롤백 대상이 아니다.** 실패한 런의 bag 도 남긴다 (05 §5.2 — 실패도 데이터다)

### 9.7 C3 적용 (2026-07-29)

`GET_STATUS` 응답을 04 §4 스키마의 **정형 JSON** 으로 바꿨다. 종전에는 한국어 문장이었고
`control_web` 이 `_STATUS_RE` 정규식으로 그걸 뜯어 **mask·ctr_mode·auto_mode 넷만** 알 수
있었다 — 조작 UI 를 그 위에 올릴 수 없던 이유가 이것이다.

**조립을 rclcpp 밖(`rd_status.{hpp,cpp}`)에 뒀다.** 스키마는 계약이므로 노드 없이
유닛 테스트되어야 한다 (A5 의 성과를 쓰는 자리).

지킨 규칙 4가지:

| 규칙 | 구현 |
|---|---|
| 모든 키가 항상 존재 | 빈 스냅샷으로도 23키 전부 나온다 (테스트가 고정) |
| 값이 없으면 `null` | **키를 빼지 않는다.** 비활성 슬롯도 `cmd`/`target`/`duration`/`attempts` 를 `null` 로 갖는다 — 키 유무로 분기하게 되면 그것이 곧 "형태로 분기하는 파싱" 이다 |
| enum 은 문자열 | 정수 원본이 필요한 곳만 별도 키 (`ecu_sys_state`) |
| `stamp_valid=false` → 품질·드리프트 `null` | 미수렴이면 그 값들은 의미가 없다 |

추가로 챙긴 것:

- **문자열 이스케이프.** `safe_stop_detail`·`lock_reason` 에는 한글·따옴표·개행이 섞여
  들어온다. 빼먹으면 **거부 사유 하나가 응답 전체를 깨뜨린다.** UTF-8 본문은 그대로 통과시키고
  제어문자만 `\u` 로 바꾼다.
- **숫자는 로케일과 무관하게** 찍는다 (`snprintf`). `std::to_string(double)` 은 소수점이
  로케일을 따라가 `0,000` 이 나올 수 있고 그러면 JSON 이 깨진다.
- NaN/inf → `null`. JSON 에 없는 값이다.

소비자 정리:

- `control_cli status` 는 **JSON 을 파싱해서** 사람용 요약을 만든다. 브리지가 사람용 문장을
  따로 만들어 주는 길을 없앤 것이 요점이다 — 그 길이 남으면 그걸 다시 정규식으로 뜯는
  소비자가 생긴다. 자동화용 원문은 `status --json`.
- `control_web` 은 응답을 **그대로 보관**한다. 키를 골라 담으면 그 부분집합이 두 번째 계약이 된다.
- 웹 UI 에 `write_span`·`read_preset`·`clock`(수렴 여부) 표시를 추가했고, **원점 버튼이 왜
  막혔는지**를 `safe_stop_detail` 로 그대로 보여준다. 종전에는 눌러 봐야 알 수 있었다.

실기 확인 (2026-07-29): 필수 키 23/23, 파이썬 `json` 파서로 파싱 성공.
`safe_stop_detail` 이 회전 중에 사유(`"거부: ControlState=STREAM …"`)를 실어 왔고,
웹 ①~⑥ 흐름은 그대로 동작한다 (slider 15 → `write=NONE` → run → 14.90 → stop 유지).

### 9.8 E3 · C2 적용 (2026-07-29)

§9.2 가 "실재하는 버그" 로 분류한 2건. 둘 다 **회귀 테스트를 구 코드에 대고 돌려

양쪽 통과).

#### E3 — `noise` 는 slew 검사 면제 (05 §3.4)

`slew_rate` 위반은 자동 성형이 아니라 **reject** 인데(§4.3-4), 백색 가우시안 잡음은 정의상
tick 간 델타가 무제한이다. **두 규칙을 함께 지키면 `noise` 세그먼트는 사실상 항상 거부된다.**

- `noise` 구간과 **그 경계 tick** 을 slew 검사에서 건너뛴다. 경계도 빼는 이유는 그 델타
  역시 잡음이 만든 것이기 때문이다. 건너뛴 수는 `slew_exempt_ticks` 로 기록한다 —
  그 구간에 레이트 제한이 없었다는 사실을 분석이 알아야 한다.
- 면제는 **`noise` 에만** 적용된다. 전역으로 풀면 §4.3-4 가 통째로 죽는다 (테스트가 고정).
- 대신 **진폭 가드**: `mean ± 4σ` 가 실효 클램프를 벗어나면 거부. 클램프가 분포의 꼬리를
  잘라내면 **재생된 잡음이 YAML 이 선언한 정규분포와 달라지는데**, 시스템 식별 입력이
  선언과 다르면 동정 결과가 틀리고 그 사실이 기록 어디에도 남지 않는다
  (`clamp_cnt` 는 숫자일 뿐 "분포가 바뀌었다" 는 뜻을 담지 못한다).
  4σ 인 이유: 720,000 tick 에서 기대 초과 약 45회 — 실무상 "거의 안 잘린다".

**실기 확인**: 어제 `53.6 A/s > 50` 으로 거부됐던 **바로 그 프로파일**을 `slew_rate: 50`
그대로 두고 완주했다. 600 tick, `clamp_cnt=0`, **`slew_exempt_ticks=401`**
(noise 2.0s@200Hz = 400 + 경계 1 — 예측과 정확히 일치).
4σ 가드도 실기에서 사유와 함께 거부했다 (`mean±4σ = [-2, 2]` vs 한계 `[-1, 1]`).

#### C2 — `once` 만료를 시간 → 시도 횟수(40)

REBOOT 성공 시 blackout 이 **3초**인데 `once` 만료는 **벽시계 2초**였다. blackout 중에는
`GetSlotTask` 가 early-return 하므로 명령이 **한 번도 시도되지 않는데** 시계는 흘렀다 —
**REBOOT 직후 예약한 명령은 시도 0회로 죽었다.**

시간이 아니라 **실제 발사 횟수**를 센다 (`kOnceMaxAttempts = 40`, 5Hz 기준 시도 8초치).
기다린 시간은 예산을 소모하지 않는다.

부수: `SlotSnapshot()` 이 `attempts` 로 `err_streak`(연속 실패)를 내보내고 있던 것을
**실제 발사 횟수**로 정정했다 — GET_STATUS 의 `slots[].attempts` 가 다른 값을 뜻하고 있었다.

> ⚠ **C2 는 실기 미검증이다.** 재현하려면 ECU 에 REBOOT 을 걸어 blackout 을 만들어야 하고,
> control 모드는 커맨드 슬롯이 0개라(04 §2.4.1) 그 경로 자체가 없다. 단위 테스트가 그
> 시나리오(시도 없이 2.2초 경과)를 결정론적으로 재현한다.

테스트: 브리지 **146** (E3 6 + C2 4 신규) / control_cli 29 / control_web 7.

### 9.10 정정 — `bridge_mode` 는 **3개다** (2026-07-29)

§9.10 이전 커밋에서 `traction` 을 4번째 열거값으로 남기고 구 불리언 두 개를 폐지 예정
별칭으로 뒀다. **둘 다 근거가 서지 않았고 되돌렸다.**

| 남겼던 이유 | 왜 틀렸나 |
|---|---|
| *"3분류는 `read_preset` 축을 전제하는데 그게 없다"* | **그 축을 같은 날 만들었다** (`rd_read_preset.hpp`). 판단이 낡은 상태로 남아 있었다 |
| *"구 불리언을 지우면 돌고 있는 스크립트가 깨진다"* | 이 브랜치는 **push 전이고 하나로 squash 될 예정**이다. 호환을 지킬 배포본이 없다 |

**`traction` 은 모드가 아니라 control 의 한 구성이다.** 01 §4.2 의 `auto_mode` 표에
`none` 이 이미 있었고, 두 태스크의 read 세그를 비교하면 traction 은 control 에서
`{128,4}` ctr_mode read-back 만 뺀 것이다.

```
구:  -p traction_test_mode:=true
신:  -p bridge_mode:=control -p auto_mode:=none -p read_preset:=control_test
```

- `BridgeMode{project|control|manual}` — 3개. 구 불리언 삭제.
- `auto_mode: none` 신설 — ECU 레지스터 값이 아니라 **브리지 표식**(0xFF)이다.
  이 값이면 INIT 의 ECU 설정 write 를 건너뛰고 200Hz tick 이 RW 대신 READ 를 낸다.
- `read_preset` 기동 파라미터 신설 (01 §4.2). `control_test` 프리셋을 추가해
  **구 traction 배치와 wire 를 바이트 단위로 보존**했다 (골든 바이트가 확인).
- `auto_mode` 를 **단어형 정본 + 정수 병행**으로 (01 §4.2). dynamic typing 을 안 걸면
  문자열로 선언한 파라미터에 `-p auto_mode:=2` 를 주는 순간 타입 불일치로 노드가 죽는다
  (실제로 exit 134 가 났다).
- 구 `task_traction_` 정의를 삭제하고 프리셋에서 파생시켰다 — 진실이 둘이면 갈라진다.

#### 기동 게이트에 구멍이 있었다

`bridge_mode` 오타가 **기본값(project)으로 조용히 떨어졌다.** 검증 플래그를 만들어 놓고
`MainLoopStart` 의 게이트가 그것을 안 봤기 때문이다 (control 일 때의 `active_motors`·
`auto_mode` 만 봤다). 모드가 틀린 채 뜨는 것은 **모터가 도는 모드인지 아닌지가 갈리는**
문제라 모드와 무관하게 막도록 고쳤다.

**실기 확인** (2026-07-29):

| 입력 | 결과 |

## 10. B1 — 엔코더 버스 진단 (2026-07-29, 실기)

W4(Tab3)가 처음 드러낸 `degraded_cnt[4]=100%` 를 레지스터 직접 판독으로 확인했다.
control 프리셋은 SYS 를 안 읽어서 이 고장이 **여태 보이지 않았다** (04 §2.3 이 전 프리셋을
`{16,17}` 로 통일한 이유가 바로 이것이다).

판독 경로: `bridge_mode:=manual` → `command set auto 3 ecu raw_read 70 16` →
`ControlConfig op=9`(OP_GET_REGISTERS) 로 256B 스냅샷.

### 관측

| 항목 | 값 | 해석 |
|---|---|---|
| `state`(addr 85) | `0x2F` | lifecycle=**15 LS_OFFLINE**, health=**2 HC_TIMEOUT** |
| `degraded_cnt[4]` | **100%** | i2c1 트랜잭션이 전부 실패 |
| `hw_error` / `hw_fatal` | `0x10` / `0x10` | bit4 = i2c1/엔코더 |
| `delta_tick[0]` | 6.8 ms | ch0 은 취득 시각이 찍혔다 |
| `delta_tick[1..4]` | `0xFF` **stale** | ch1~4 는 한 번도 못 받았다 |
| `encoder[0..4]` raw | 3849 / 3215 / 250 / 1784 / 256 | 전부 12bit 범위 안이지만 **stale 잔값**이다 |

### 무엇을 말해 주는가

**ch0 만 응답하고 ch1~4 가 타임아웃**이다. AS5600 5채널은 I2C MUX 로 순차 취득하므로,
"MUX 이후 채널이 안 붙었다"(배선·MUX 전원·주소 충돌) 쪽을 먼저 본다. 버스 전체가 죽었다면
`delta_tick[0]` 도 `0xFF` 여야 한다.

⚠ **raw 값이 그럴듯하다고 살아 있다고 읽으면 안 된다.** 12bit 범위 안의 값이 들어 있지만
`delta_tick` 이 stale 이라 **언제 찍힌 값인지 모른다.** 값의 그럴듯함이 아니라 stale 플래그가
판정 기준이다 — 03 §5.3 의 "미판독과 정상 0 을 구분한다" 와 같은 문제다.

### 지금 상태에서 하면 안 되는 것

- `link_angle` 을 쓰는 실험 (03 §8.2 MPC 입력 포함). 어차피 지금은 어떤 프리셋도 엔코더를
  안 읽어 NaN 이지만(§9.9), 프리셋을 되살려도 **값 자체가 못 믿을 것**이다.
- `degraded_cnt`/`hw_error` 를 "원래 그런 것" 으로 넘기기. 이건 상시 표시돼야 한다.

### 남은 일

**하드웨어 점검이 먼저다** (I2C MUX 전원·배선·풀업). 소프트웨어 쪽에서 더 알아낼 것은 없다 —
ECU 가 이미 채널별 stale 플래그로 정확히 보고하고 있다.
