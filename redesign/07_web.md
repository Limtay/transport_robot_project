# 07 — control_web 재설계 (조작 UI 를 정본 인터페이스로)

> 2026-07-29 착수. 00~06 의 후속. **웹은 사용자용, CLI 는 AI·자동화용** 이라는 역할 분담을
> 전제로, 지금까지 CLI 로만 되던 것을 웹에서 시각적으로 하게 만든다.
>
> 선행 조건이던 **C3(GET_STATUS 정형 JSON)** 은 06 §9.7 에서 끝났다. 웹이 브리지 상태를
> 문자열 정규식이 아니라 구조로 읽을 수 있게 됐으므로, 그 위에 조작 UI 를 올릴 수 있다.

## 1. 무엇이 바뀌는가 — 웹이 브리지의 **상위** 가 된다

종전 `control_web` 은 이미 떠 있는 브리지에 **붙는** 클라이언트였다. 그래서 기동 파라미터로
정해지는 것(`bridge_mode`·`read_preset`·`active_motors`)은 손댈 수 없었고, 이것이 06 §9.1 이
지적한 "웹 기능이 제한적인" 이유의 나머지 절반이다.

**웹이 브리지를 띄우는 주체가 된다.**

```
종전:  [터미널] ros2 run … comm_test_node  →  [브라우저] 붙어서 조작
확정:  [브라우저] 모드 고르고 [적용]  →  control_web 이 브리지를 spawn  →  조작
                                      [정지] / [다시 시작] 도 웹에서
```

01 **Q2("bridge_mode 는 기동 시 고정, 변경 = 재시작")를 뒤집지 않는다.** 재시작은 여전히
재시작이고, 다만 그 재시작을 사람이 터미널에서 하던 것을 웹이 대신한다. 프레임·프리셋을
런타임에 갈아끼우는 일은 하지 않는다 — 실험 시계열이 중간에 갈라지기 때문이다.

`control_web` 이 브리지와 **별도 프로세스**(자기 rclpy 노드)라서 성립한다. 웹 서버가
브리지 노드 안에 있었다면 자기를 죽여야 해서 불가능했을 것이다.

### 1.1 그 대가 — 웹이 먼저 뜨고 혼자 살아야 한다

지금 `control_web` 은 브리지가 있다고 **가정한다.** 상태 폴링이 실패하면 그냥 기본값이 남고,
UI 는 "브리지가 없다" 와 "브리지가 대답을 늦게 한다" 를 구분하지 못한다.

→ **`bridge_proc` 를 1급 상태로 만든다.** `stopped` / `starting` / `running` / `exited(rc)`.
   `stopped` 에서는 조작 UI 전체가 비활성이고, 모드 선택과 [시작] 만 살아 있다.

### 1.2 기동 실패를 사람이 볼 수 있어야 한다

06 §9.10 에서 기동 게이트를 조였다 — `bridge_mode` 오타·`read_preset` 오타·`auto_mode`
오타는 전부 **exit 1** 이다. 그 사유는 브리지 stderr 에만 있다. 웹이 그것을 캡처해 보여주지
않으면 사용자에게는 **"[시작] 을 눌렀는데 아무 일도 안 일어난다"** 로 보인다.

→ 웹은 브리지의 stdout/stderr 를 링버퍼(최근 200줄)에 담고 UI 하단 로그 패널에 흘린다.
   비정상 종료 시 마지막 줄들을 **모달로 띄운다** — 조용히 실패하지 않게.

### 1.3 정지 순서 — 그냥 죽이지 않는다

```
[정지] → ① OP_SET_STREAM_ARM(0)  (STREAM 이면 먼저 빠져나온다)
       → ② 200ms 대기 후 control_state 확인
       → ③ SIGINT  → 3s 안에 안 죽으면 SIGTERM → 다시 3s 후 SIGKILL
```

AK 모터의 CAN timeout(200ms)이 최종 안전망이지만 **거기에 의존해 설계하지 않는다.**
안전망은 마지막 방어선이지 정상 경로가 아니다.

### 1.4 고아 프로세스

웹이 죽으면 spawn 한 브리지가 남는다. 다시 켜서 [시작] 을 누르면 같은 토픽에 노드가 둘이 된다.

→ 웹은 기동 시·[시작] 직전에 **같은 이름의 노드가 이미 그래프에 있는지 확인**하고,
   있으면 시작을 거부하며 "이미 떠 있다 (PID 미상 — 터미널에서 내릴 것)" 을 알린다.
   `atexit` 로 자식도 정리한다.

## 2. 탭 구성

### Tab1 — 실시간

| 영역 | 내용 | 지금 되나 |
|---|---|---|
| 기동 | `bridge_mode` · `auto_mode` · `read_preset` · `active_motors` 선택 → [시작]/[정지] | **신규** (§1) |
| 런타임 | `auto_mode` 변경 (IDLE 한정) | ✅ `OP_SET_AUTO_MODE` 이미 있음 |
| | `read_preset` 변경 (IDLE 한정) | ✅ `OP_SET_READ_PRESET` (06 §4.13) |
| | 모터별 `ctr_mode` | ✅ `OP_SET_CTR_MODE` (DIRECT 한정) |
| 조작 | 모터 슬라이더 ×4 + throttle 체크박스 | 슬라이더는 있음 / **throttle 신규** |
| | [Run]/[Stop] | ✅ `OP_SET_STREAM_ARM` |
| | [원점] | ✅ `OP_SET_ORIGIN` |
| 모니터 | 필드 트리 체크 → 실시간 플롯 | **신규** (§4) |

**throttle 체크박스**: 슬라이더에서 손을 뗐을 때의 거동이다.
- **on (스로틀)** — 놓으면 **0 으로 복귀.** 자동차 액셀. 잡고 있는 동안만 명령이 산다.
- **off (setpoint 유지)** — 놓아도 값이 남는다. 현재 거동.

`position` 에서는 0 복귀가 "원점으로 돌아가라" 가 되어 위험하다 →
**throttle 은 `current`/`velocity` 에서만 켤 수 있다.** UI 가 모드에 따라 잠근다.

### Tab2 — 계획형

- 세그먼트 그래프 편집기 → **프로파일 YAML 조립** → `RunProfile` 액션 (`profile_yaml` 문자열)
  - 액션이 이미 YAML 문자열을 받으므로 CLI 를 거치지 않는다.
- 기동/런타임 선택은 Tab1 과 **같은 컴포넌트를 공유**한다 (진실이 둘이면 갈라진다).
- **기록**: `control_cli/record.py` 를 공유 모듈로 쓴다 (`control_web` → `control_cli` 의존).
  웹으로 돌린 런도 CLI 와 **동일한 schema v2 `result.json` + bag** 이 남아 분석 파이프라인에
  그대로 들어간다. 기록 로직을 웹에 다시 짜면 두 벌이 되고, 그 순간 v3 가 갈라진다.

### Tab3 — 레지스터 맵 / 커맨드 슬롯

> **⚠ 벽이 하나 더 있었다 (2026-07-29 실기 확인).** `user_slot_mask` 로 스케줄 층을 뚫고
> control 에서 레지스터 READ 를 쏘면 정책 층이 막는다:
> `"거부: raw 주소 명령은 manual 전용이다 (B6)"`.
>
> 그리고 그 정책의 근거인 **03 §7.3 의 `CommandSet.srv` 재정의가 구현된 적이 없다.**
> 지금 srv 는 여전히 raw 형태(`inst` + `start_addr`)이고, 브리지는 그 위에 게이트만
> 얹어 놓았다 — 03 §7.2 가 채택한 **(c) 혼합** 의 절반만 있는 상태다.
> §9 감사가 놓친 항목이다.
>
> | 03 §7.3 이 정한 것 | 현재 |
> |---|---|
> | `CMD_READ_SYS/MOTOR/SENSOR/DIAG/ALL` — 의미 단위 READ, **safe_stop 불필요** | 없음 |
> | `CMD_SET_MOTOR_MASK/MODE/AUTO_MODE/…` — 의미 단위 WRITE | 없음 |
> | `CMD_RAW_READ/WRITE` — **manual 전용** | 이것만 있고, 전부가 raw 취급 |
>
> **결정 (사용자, 2026-07-29): B6 을 구현한다.** Tab3 의 실시간 테이블은 `CMD_READ_*`
> 의미 단위 READ 로 채우고 control 에서 정당하게 허용한다. raw 쓰기는 manual 전용으로
> 남는다. 주소를 아는 주체가 브리지 하나로 좁혀진다는 B6 의 요점이 유지된다.
>
> **미해결**: `CMD_READ_ALL {0,256}` 은 응답 256B 로 현재 상한(`kMaxRespPayload = 88`)을
> 넘는다. 03 §7.3 자신이 *"버퍼 확장 후 1 트랜잭션"* 이라 단서를 달았으나, 2026-07-27 에
> 확장한 것은 STM **RX**(요청) 쪽이다. 응답 쪽 여유는 STM 소스를 봐야 알고, 안 되면
> 테이블을 3~4회로 나눠 읽는다.

CLI 의 `raw`·`command` 로 하던 것을 시각화한다.

- **실시간 레지스터 테이블** — 256B 전체를 필드 단위로. 값·주소·타입·R/W 를 한 행에.
  - 현재 프리셋이 **읽지 않는 구간은 미판독(회색)** 으로. `ReadPreset::Covers()` 가 이미
    이 질문에 답할 수 있다. 0 으로 그리면 06 §4.11 의 결함이 표로 부활한다.
- **쓰기** — write 영역(§3.2)의 셀만 편집 가능. 값을 채우고 → **보낼 구간을 선택** → [전송].
- **커맨드 슬롯 카드 ×4** — target / inst(READ·WRITE_REG·WRITE_DATA·REBOOT) /
  addr / len / data / duration(`once` · `forever` · N초). `CommandSet` 그대로.
- **Reboot** — ECU. DPC·PCU 는 TODO (레지스터 미확정, 04 §6).

## 3. 선행 작업 — 브리지 쪽

### 3.1 C1 나머지 (06 §9.9 정정)

06 §9.9 는 "C1 완료" 로 적었으나 **04 §2.2.1 이 명시적으로 거부한 통합 enum** 으로 구현됐다.
Tab3 가 control 모드에서 동작하려면 이 나머지가 필요하다.

| 항목 | 04 문서 | 현재 | 왜 지금 필요한가 |
|---|---|---|---|
| `SlotId × SlotInst` 직교 분해 | §2.2.1 | 통합 enum (`ECU_100HZ`, `ECU_CMDVEL`, …) | Tab3 의 READ/WRITE/REBOOT 가 곧 `SlotInst` 다 |
| 슬롯이 `ReadSpan`/`WriteSpan` 소유 | §2.2.1 | 프레임 밖 프리셋 1개 | 슬롯 구조 = 명령 구조. UI 카드가 그대로 매핑된다 |
| `FrameDef.user_slot_mask` | §2.2 (`0b0101010000`) | 없음 | **control 에서 커맨드를 쓸 유일한 경로** |

### 3.2 control 에서 1 tick 훔치기

control 프레임은 전 칸이 `ECU_CONTROL` 이라 비울 칸이 없다. `user_slot_mask` 로
**"이 칸은 양보 가능" 을 표에 적고, 커맨드가 대기 중일 때만 1 tick 을 훔친다.**

- 5ms 한 tick 의 제어 write 가 빠진다. AK CAN timeout(200ms)에 비해 40배 여유다.
- 그러나 **실험 시계열에는 구멍이 된다** → `IDLE 에서만` 허용한다.
  RUNNING/STREAM 중 거부는 `ControlConfig` 의 기존 정책과 같다.
- 게이트("지금 해도 되는가")는 **표에 넣지 않는다** — 06 §9.9 에서 세운 경계를 지킨다.
  표는 "이번에 무엇을 할 차례인가" 만 답한다.

### 3.3 레지스터 맵 메타데이터를 브라우저가 알아야 한다

지금 필드 단위 정의는 `rd_register_ecu.hpp` 의 C++ 구조체뿐이다. **JS 에 손으로 옮겨 적으면
확실히 갈라진다** — 이번 재설계에서만 표시 드리프트를 이미 한 번 고쳤다 (06 §9.7 이전).

→ `www/regmap.json` 을 두되 **드리프트를 테스트가 잡는다**:
   블록별 필드 바이트 합 == 헤더의 `REG_*_SIZE`, 오프셋 연속·비중첩, 총합 256.
   헤더의 상수는 정규식으로 뽑는다 (C++ 파서를 만들지 않는다 — 검증에 그만한 것이 필요 없다).

R/W 는 사실상 블록 단위다:

| 쓰기 가능 | `CMD_MOTOR` 128:52 · `CMD_SYSTEM` 180:13 |
|---|---|
| 읽기 전용 | `DEFINE` 0:16 · `SYS` 16:17 · `LOADCELL` 42:6 · `IMU` 48:22 · `ENCODER` 70:16 · `UART2` 86:1 · `RC` 87:1 · `MOTOR_DATA` 88:40 · `DIAG` 224:32 |
| 예약 | `RSVD0` 33:9 · `RSVD1` 193:31 |

## 4. 모니터링 — plotjuggler 방식

### 4.1 전송

현재는 브라우저가 0.5s 폴링하고 **스냅샷만** 받는다. 시계열이 없다.

- **SSE** (`text/event-stream`). 표준 라이브러리로 되고 단방향이라 이 용도에 맞다.
  WebSocket 은 `http.server` 위에서 직접 구현해야 하는데 얻는 것이 없다.
- **`ThreadingHTTPServer` 로 교체** — 지금은 단일 스레드라 SSE 연결 하나가 다른 요청을
  전부 막는다. 이걸 안 바꾸면 스트림을 여는 순간 UI 가 굳는다.
- **다운샘플**: 200Hz 를 그대로 보내지 않는다. 기본 **50Hz**, 구간 내 **min/max 보존**
  (평균만 내면 스파이크가 사라지고, 스파이크가 이 실험의 관심사다).

### 4.2 필드 열거는 자동으로

`ControlFeedback` 은 40 필드 · 배열 펼치면 90여 계열이다. 손으로 적으면 메시지가 바뀔 때
갈라진다 → **`rosidl` 내성으로 필드를 열거**한다. 배열은 `fb_current[0..3]` 처럼 펼친다.

### 4.3 미판독은 선을 끊는다

`255`(uint8) / `NaN`(float) 은 **미판독**이다. 플롯에서 0 으로 찍으면 이 프로젝트가 반복해서
지워 온 결함(안 읽은 값이 정상값처럼 보이는 것)이 그래프로 되살아난다.
→ SSE 페이로드에서 `null`, uPlot 에서 **gap**.

### 4.4 차트

**uPlot vendoring** (`www/vendor/uplot.*`, ~40KB). 로봇은 오프라인이라 CDN 을 쓸 수 없다.

## 5. 작업 순서

| 단계 | 내용 | 검증 |
|---|---|---|
| **W0** | §3.1 C1 나머지 + §3.2 control 1 tick steal | 유닛(스케줄 골든 갱신) + **실기: steal 중 주기 초과 0** |
| **W1** | 감독자 — spawn/stop, 로그 캡처, `bridge_proc` 상태, 고아 탐지 | 실기: 오타 파라미터로 [시작] → 모달에 사유 |
| **W2** | `ThreadingHTTPServer` + SSE + 필드 자동 열거 + 다운샘플 | 실기: 50Hz 스트림, 미판독 null |

| **W4** | Tab3 — regmap.json(+드리프트 테스트) · 테이블 · 슬롯 카드 | 실기: control 에서 READ 성공 |
| **W5** ✅ | Tab2 — 그래프 편집 → YAML → `RunProfile` + `record.py` 공유 | 실기: 웹 런의 `result.json` 이 CLI 와 **키 21개·타입 전부 동일** |

### 5.1 W5 에서 나온 것 (2026-07-29)

**① 기록 매핑을 다시 짰다가 8개를 빠뜨렸다.** action Result → `result.json` 매핑을 웹 쪽에
따로 적었더니 `mode`·`seed`·`irregular_tick_cnt`·`drop_cnt`·`slew_exempt_ticks`·
`clock_converged`·`drift_ppm` + `node_params` 가 통째로 빠졌다. 전부 **브리지만 아는 값**이라
(05 §5.3) 없으면 나중에 지어낼 수도 없다. `record.result_from_action()` 하나로 합쳤고,
CLI 도 그것을 쓴다. `start_bag`/`stop_bag`/`bridge_node_params` 도 같은 이유로 record 로 옮겼다.

> 이 세션에서 같은 형태의 사고가 세 번 나왔다 (`kMaxRespPayload=88`, `ShadowBase` static,
> 이 매핑). **"두 곳에 적으면 갈라진다" 는 경고가 아니라 관측이다.**

**② bag 경로가 웹의 CWD 기준이었다.** `ros2 run` 이 어디서 뜨느냐에 따라 달라지는데 CLI 는
보통 레포 루트에서 돈다 → 웹으로 돌린 런만 다른 곳에 쌓이고, 그건 분석할 때가 되어서야
드러난다. `bag_dir` 파라미터로 빼고 **해석된 절대경로를 기동 로그에 남긴다.**

**W0 이 먼저인 이유**: 브리지 쪽이고 웹 전체가 그 위에 얹히며, 유일하게 **실기 타이밍
재검증이 필요한 항목**이다. 여기서 문제가 나오면 Tab3 설계가 통째로 바뀐다.
