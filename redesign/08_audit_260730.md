`include/orin_firmware_bridge/rd_common.hpp:61` — `HW_BIT_UART4` 그대로다.

## 6. 이 감사가 남기는 것

06 §9 가 놓친 두 가지 형태가 이번에 드러났다. 다음 감사도 같은 것을 놓치지 않으려면:

- **"완료" 표시를 근거로 대조를 건너뛰지 않는다** (§2.1). 커밋 내역 표에 적혀 있다고
  코드에 들어간 것이 아니다. `HW_BIT_UART6` 는 **사용처가 없어 테스트가 영원히 못 잡는**
  종류라 사람이 볼 수밖에 없었다.
- **감사 범위를 브리지 밖까지 넓힌다** (§2.3). `analysis/`·`data/` 는 재설계 문서의
  결정(개명)에 직접 영향을 받는데 06 §9 표에는 한 줄도 없었다. 계약을 바꾸면
  **소비자 전부**를 세어야 한다.

> 07 §5.1 이 적은 *"두 곳에 적으면 갈라진다 는 경고가 아니라 관측이다"* 의 다른 얼굴이다.

### 디코더 설계가 옳았다는 증거

IMU 가 stale 로 나와 게이트가 틀린 것인지 확인했다:

```
lc[2]/hs[2] (uart6/IMU) = 1/0     → ECU 는 "정상" 이라고 보고
imu.delta_tick          = 0xFF    → stale
/carrier_imu raw        = 전부 0 (사원수 w=0)  ← 물리적으로 불가능
```

**데이터가 실제로 안 온다.** `delta_tick` 은 데이터와 일치하고 `lc/hs` 만 틀렸다.
`lc/hs` 로 게이트했다면 `quat=(0,0,0,0)` 을 유효한 자세로 발행했을 것이다.

## 8.2 ★ 실기로만 드러난 결함 — 읽기 전용 control 이 INIT 을 못 벗어난다

`rd_schedule.cpp` 의 `read_only_control` 분기가 `MarkInitDone()` 도 `on_init_done_()` 도
부르지 않았다. 13,655 tick(68초) 동안 `control_state = 0 (INIT)` 이었다.

바로 아래 `manual` 분기에는 같은 문제를 인지한 주석이 있다 — *"INIT 에 머물면 config
service 가 통째로 막힌다"*. **manual 만 고쳐졌고 read-only 는 빠져 있었다.**
커밋된 코드도 동일하므로 §7 변경과 무관한 기존 결함이다.

**`./run.sh traction` 이 정확히 이 구성이다.** 피해:

| | 증상 |
|---|---|
| `cli status` | 완전 실패 (config 서비스가 안 만들어진다) |
| `cli config preset` | 불가 — SET_READ_PRESET 이 이 모드에서 무용 |
| 웹 Tab1 | `control_state=INIT`, `auto_mode=current`(**틀림**), `read_preset=-` |
| 웹 Tab3 | **완전히 죽음** (OP_GET_REGISTERS 가 그 서비스를 탄다) |
| bag 전 메시지 | `control_state=0`, `auto_mode=1(CURRENT)` — **쓰지 않은 런이 "전류를 쓴 런" 으로 기록** |

### 적용 — A안 (서버 분리)

`RdControlApi` 에 읽기 전용 거부 로직이 **없다.** 그래서 단순히 `on_init_done_()` 을 부르면
프로파일 goal 이 수락되는데 write 가 없어 아무 일도 안 일어난다 — 거부보다 나쁘다.
그래서 **열릴 조건이 다른 두 서버를 분리**했다:

- `StartConfigService()` — control 이면 **항상**. 상태를 못 읽으면 조작자가 눈을 잃는다.
- `StartProfileServer()` — **명령을 쓰는 구성에서만**. (config 를 먼저 보장한다.)

`on_init_done` 시그니처를 `void(bool with_profiles)` 로 바꿔 스케줄러가 알린다.
`manual` 도 `false` 로 고쳤다 — `WritesCommands()` 가 false 이고 프레임에 write 슬롯이 없다.
읽기 전용 분기는 `SetAutoMode(AUTO_MODE_NONE)` + `SetReadPreset()` 도 함께 한다.

**검증 결과**: `INIT -> IDLE` / `config service 준비됨` / `cli status` 동작 /
`ros2 action list` **비어 있음**(재생 서버 안 열림 = 의도대로) / `control_state=1`,
`auto_mode=255(none)` / `config preset 0` 런타임 교체 성공(응답 123B).

### 곁가지 2건

**`auto_mode=none` 이 "unknown" 으로 표시됐다.** `AutoModeName`/`AutoModeJsonName` 표에
`0xFF` 가 없었다. `none` 은 유효한 선택지인데 조작자에게는 고장처럼 보이고,
`result.json` 의 `mode` 에도 "unknown" 으로 남아 분석이 그 런을 분류하지 못한다.

**`/carrier_imu` 가 `(0,0,0,0)` 을 유효한 자세로 발행하고 있었다.** 가드가
`lifecycle == LS_OFFLINE` 하나였고 위 §8.1 대로 그것이 안 걸렸다. `delta_tick` +
`Reads()` + `LS_OFFLINE` 셋으로 바꾸고, 미판독이면 NaN + `covariance[0] = -1`(REP-145).

> ### ⚠ 그 과정에서 한 층 더 깊은 함정이 나왔다
>
> `delta_tick` 만으로 고쳤더니 **여전히 0이 발행됐다.** 섀도가 0으로 초기화되므로
> **한 번도 안 읽은 블록은 `delta_tick == 0`, 즉 "지연 0ms = 아주 신선함"** 으로 보인다.
> 견인 프리셋(`control_test`)은 IMU 를 안 읽으므로 그 초기값 0이 그대로 통과한 것이다.
>
> `Reads()` 를 **맨 앞에** 두어야 한다. "미판독과 정상 0 을 섞지 않는다"(03 §5.3)가
> 발행 층뿐 아니라 **섀도 초기화 층에서도** 필요하다는 뜻이다.
> `OnFeedback()` 은 처음부터 `Reads()` 로 시작해서 이 문제가 없었다.

# 9. DPC 레지스터 맵 반영 + 전개 시퀀스 (2026-07-30)

진실 원천: 구글시트 `Register_DPC` 탭. `enable_dpc_read_=false` 로 막혀 있던 §4 의
"C5 DPC/PCU 레이아웃 — 레지스터 미확정" 이 해소됐다.

## 9.1 ★ C5 는 **채택되지 않았다** — DPC SYS 는 ECU 와 다르다

04 §6.2 는 세 보드의 SYS 를 `16:17` 로 통일하자고 제안했다. 확정된 맵은 그것이 아니다:

| | ECU | DPC |
|---|---|---|
| SYS 위치·크기 | `16 : 17` | **`46 : 16`** |
| hw_* 순서 | error(24) fatal(25) reset(26) | **reset(54) fatal(55) error(56)** ← 역순 |
| `rs485_proc_delta` | 있음(28) | **없음** |
| `realtime_tick` | ×0.1ms (TIM5 10kHz) | **ms (TIM5 1kHz)** ← 10배 |
| `sys_state` | 0=INIT 1=MANUAL 2=AUTO 3=ESTOP_SW 4=ESTOP_HW 5=FAULT | **0=CTRL 1=HOLD 2~8=DEPLOY_FSM 10=FAULT** |
| degraded_cnt 채널 | 0=uart1 1=uart2 2=uart6 3=can1 4=i2c1 | **0=uart2 1=uart4 2=uart6 3=i2c1** |

**04 §6.2 가 예고한 대가를 그대로 치른다** — 그 절의 대안 문구가 그대로 발동된다
(*"거부되면 rd_telemetry 에 보드별 매핑 함수를 두는 것으로 대체 가능, 비용은 그만큼 증가"*):

- `NodeStatus` 매핑을 **보드별로** 해야 한다. 공통 `{16,17}` 세그가 성립하지 않는다
- **시간 동기(B1) 확장이 막혔다**: `proc_delta` 가 없고 tick 단위가 10배 다르다
- `lc[]`/`hs[]` 인덱스 = 통신 채널 규약은 유지되나 **보드별 채널 매핑표**가 필요하다

## 9.2 ★ DPC-A / DPC-B ID 가 **반대로 적혀 있었다**

| | 시트(정본) | 종전 코드 |
|---|---|---|
| DPC-A | 0xD2 | 0xD1 |
| DPC-B | 0xD1 | 0xD2 |

`TARGET::DPC` 는 `PacketID::DPC_B` 를 가리키므로, **정정 전 브리지는 0xD2(= 실제 DPC-A)를
부르면서 DPC-B 의 레지스터 맵을 기대하고 있었다.** `enable_dpc_read_=false` 라 실기에서
드러나지 않았을 뿐이다. 사용자 확인을 거쳐 시트 쪽으로 정정했다.

(`PRA = 0xA1` 은 시트 표기이고 코드는 `PCU` 로 부른다 — 같은 보드인지 미확인.)

## 9.3 `rd_register_dpc.hpp` 전면 재작성

골격(84줄, SYS 16B 중 2바이트만 정의)을 실제 맵으로 교체했다. 이 맵은 **DPC-B 의 맵이고
DPC-A 의 데이터를 함께 싣는다** (`[DPCA/data]` 62~64, `[DPCA/cmd]` 120~121).

크기 `static_assert` 11개에 더해 **`offsetof` 검사 11개**를 넣었다 — 크기만 보면
**필드 순서 변경을 못 잡는다** (01 §9.1 에서 ECU 헤더로 이미 겪은 함정이다).
시퀀스가 쓰는 두 주소(`sys_state` 57 / `sys_state_target` 127)는 절대주소로 따로 못박았다.

두 가지 함정을 만났다:

1. **시트 총합이 255B 다.** 마지막 RESERVED 가 `207 | 48` 인데 그러면 1바이트가 뜬다.
   머리말의 "Total 256 byte" 에 맞춰 **49** 로 두었고, static_assert 가 이 판단을 강제한다.
   → 시트 쪽 확인 필요.
2. `HW_BIT_UART2` 같은 이름을 DPC 네임스페이스에 `constexpr` 로 두자 **컴파일이 깨졌다** —
   ECU 쪽 같은 이름이 `rd_common.hpp` 의 **전역 매크로**라 네임스페이스와 무관하게 치환된다.
   `kHwBitUart2` 로 개명했다.

## 9.4 전개 시퀀스 — 골격 완성, 값만 대기

사용자 결정: *"골격만 만들고 대기"* (DEPLOY_FSM 2~8 의 개별 의미가 시트에 없다).

`ISlotHost` 를 확장했다:
- `PostAutoWrite(addr,value)` → **`PostAutoWriteTo(target,addr,value)`** (ECU 전용이었다)
- **`DpcSysState(uint8_t*)`** 신설 — 값과 **신선도를 함께** 준다

> ⚠ 신선도를 함께 주는 것이 핵심이다. DPC 섀도는 0으로 초기화되는데 **`sys_state == 0` 은
> `CTRL`(정상 기본값)** 이라, 값만 돌려주면 시퀀스가 **읽지도 않은 0을 보고 "이미 도착했다"**
> 고 판정한다. IMU 에서 같은 함정을 이미 밟았다(§8.2) — 이번엔 처음부터 막았다.
> 기준은 `dpc.comm.is_connected`(= 성공한 트랜잭션이 한 번이라도 있었는가).

구현한 5단계 (`CAMERA_ACTION` 만 TODO — **카메라 미연결**):

| 단계 | 하는 일 |
|---|---|
| `DPC_STATE_CHECK` | 목표값 설정 확인 → 읽힘 확인 → FAULT 아님 → **이미 전개 구간이면 거부** |
| `DPC_DEPLOY` | `sys_state_target`(127) 에 `deploy_target` write |
| `DPC_WAIT_CAMERA` | `sys_state == camera_ready` 대기 |
| `CAMERA_ACTION` | **TODO** — 통과하되 경고 로그를 남긴다 (조용히 건너뛰면 나중에 시퀀스 밖에서 찾게 된다) |
| `DPC_RETRACT` / `DPC_WAIT_RETRACT` | 회수 요청 + 완료 대기 |

**DEPLOY_FSM 값을 코드에 박지 않았다.** `DeployTargets` 로 주입하고, 미설정이면
`DPC_STATE_CHECK` 가 **전개를 시작하지 않는다.** 임의값을 기본으로 박아 두면 확정 전에
누가 돌렸을 때 엉뚱한 전개 동작이 나간다 — 모르는 것은 모른다고 두는 편이 안전하다.

대기 단계는 전부 **타임아웃(30초)** 을 갖는다. 전개 도중 매달려 있는 것이 가장 나쁘다.

### `/jeongae` 토픽의 DPC write 를 뺐다

`rd_carrier_api.cpp` 가 `dpc.reg.cmd.cmd_jeongae` 에 쓰고 있었는데, 그건 미확정 시절의
**골격 스텁**이고 실제 맵에 그런 필드는 없다. **어차피 아무 데도 가지 않았다** — 프레임에
DPC WRITE 슬롯이 없고 읽기도 꺼져 있었다. 되살리려면 어느 필드에 매핑할지가 곧 액추에이터
동작을 정하는 결정이라, 확인 전까지 쓰지 않는다. 전개의 정본 경로는 `RdSequence` 다.

## 9.7 정정 — 펌웨어 헤더 `rd_register_dpcb.h` 수령 (2026-07-30 오후)

시트만 보고 옮겼던 것을 **펌웨어 헤더가 정본**이므로 그쪽으로 맞췄다. 네 가지가 달랐다.

### ① DPC ID 는 **0xE2** 다

> ⚠ **이 절은 이력이다. 현행 값이 아니다.** 2026-08-03 에 DPC-B ID 는 **0xD1** 로 재확정됐다
> (펌웨어 `ORIN_MY_ID` 가 정본, 브리지 `PacketID::DPC_B` 가 미러).
> 자세한 경위와 변경 지점 목록은 `dpcb_config_wiki/plan_260803_orin_comm_fix.md` §Phase A 참조.

시트 ID 표(0xD1/0xD2)도 낡았다. `ECU 0xE1 / DPC-B 0xE2` 연번이 지금 배치다.
정정 전 브리지는 **존재하지 않는 주소**를 부르고 있었다 (읽기가 꺼져 있어 안 드러났다).
`DPC_A` 는 브리지가 직접 부르지 않는다 — DPC-B 가 UART4 로 중계한다.

### ② DIAG 는 **32B** 다 (진단 4 + 확장 예약 28)

시트를 4B 로 읽어 마지막 RESERVED 를 49 로 **추정**했었다. 헤더 확인 결과
`REG_DIAG_SIZE=32` / `RSVD3=49` 가 맞다 — **추정이 맞았고 시트의 "48" 이 오타였다.**
`static_assert` 가 총합 256 을 강제한 덕에 추정 지점이 명시적으로 남아 있었다.

### ③ `ex_sw` 는 배열이고 **SPDT 값이 시트와 다르다**

시트: `0=UP 1=IDLE 2=DOWN` / 헤더: **`0=IDLE(mid) 1=UP 2=DOWN`**. 헤더를 따랐다.
`hardware_error[3]` 도 `int8_t` → `uint8_t`.

### ④ ★ `DPCB_STATE_e` 확정 — 시퀀스가 완성됐다

```
CTRL(0) ──target=INIT(2)──▶ INIT ▶ DESCEND_1(3) ▶ DESCEND_2(4) ▶ WAIT(5)
                                                                   │
                                       Orin 이 target=ASCEND_1(6) 을 써야 전이
                                                                   ▼
CTRL(0) ◀──자동 복귀── FINISH(8) ◀ ASCEND_2(7) ◀ ASCEND_1(6) ◀──────┘
                                          ERROR(10) = FSM 실패/통신 FAULT
```

- **`WAIT(5)` 가 카메라 위치다.** FSM 이 거기서 멈춰 Orin 을 기다린다 — `CAMERA_ACTION`
  이 들어갈 자리가 정확히 그 지점이고, 카메라가 없는 지금도 DPC 는 서두르지 않는다.
- **Orin 이 쓸 수 있는 값은 넷뿐이다**: `CTRL(0)/HOLD(1)/INIT(2)/ASCEND_1(6)`.
  나머지는 DPC 가 스스로 밟는 중간 상태라 밖에서 쓰면 단계를 건너뛴다.
  `IsWritableTarget()` 로 막고, 테스트가 "시퀀스의 모든 DPC write 가 mask 안" 을 고정한다.
- **브리지가 쓰는 것은 두 번뿐이다** (INIT / ASCEND_1). 나머지는 `sys_state` 로 따라간다.
