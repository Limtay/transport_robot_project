### 0.3 ⚠⚠ project 모드는 주행이 불가능했다 (2026-08-05 실기) — **해소됨**

§0.0 을 고치고 실기로 확인하다 드러났다. cmd_vel 이 ECU 에 **한 번도 도달한 적이 없다.**

```
[Map Warn] RW write rejected: [Access Error]   ← 100% 거부, 200 tick 마다 반복
```

원인 사슬:

1. `RD_MAP_DISPATCH_WRITE` 는 cmd_vel 구간 쓰기를 `mtr_lock` 으로 막는다.
   `mtr_lock = (robot_state != SYS_STATE_AUTO)` (`ECU_V3/rd_system.c:678`).
   즉 **ECU 가 AUTO 가 아니면 cmd_vel 쓰기는 거부**된다.
2. ECU 를 AUTO 로 올리는 것은 브리지 INIT 의 `mode(190)=AUTO` write 인데,
   **project 모드는 INIT 자체를 안 한다** — `rd_schedule.cpp` 의 분기는
   `read_only_control` / `control` / `manual` 셋만 처리하고 project 는 마지막 `else`
   (로그 한 줄)로 빠진다.
3. 그 `else` 는 `on_init_done_` 도 안 부른다 → **`/carrier/control/config` 서비스가
   아예 안 열린다.** 그래서 CLI 로 수동으로 AUTO 를 올릴 수도 없다:
   `ERROR: config 서비스(/carrier/control/config) 없음`.

> 이것은 `06 §9.9` 의 *"Q3 … 실기 타이밍 확인, **주행 검증은 미실시**"* 와 정확히 맞는다.
> project 는 **기본 모드**인데 주행 경로가 한 번도 돌아간 적이 없다.

**→ 해소 (2026-08-05, 사용자 지시로 §4.3 구현).** 위 ①②를 함께 했다:
`InitProject()` 가 `mode=AUTO` 를 쓰고, `MarkInitDone()` + `on_init_done_(false)` 로
FSM 과 config 서비스도 연다. 실기 확인 — INIT 3단계 통과 · `ecu=auto` · `control_cli status` 동작.

**단, cmd_vel 수락은 아직 미검증이다.** `mode=AUTO` 만으로는 부족하고 ECU 가
`SYS_STATE_ESTOP_SW` 에서 나와야 하는데, 복귀 조건이 `!motor_fault && health < WARN`
(`ECU_V3/rd_system.c:457`) 이라 **모터가 CAN 에 붙어야 한다.** ECU 가 설계대로 동작하는
것이며("모터 부재 시 AUTO 주행 금지"), 모터 연결 회차로 미뤘다 (사용자 결정).

## 1. ECU 읽기 프리셋 재편

### 1.1 메모가 정한 배치

| 프리셋 | 현행 | 확정 | payload |
|---|---|---|---|
| `control` | `{16,17}{42,86}{128,4}{164,16}` | **`{16,17}{48,80}`** | 123B → **97B** |
| `diag` | `{0,33}{128,4}{224,32}` | **`{0,33}{128,4}{188,4}{224,16}`** | 69B → **57B** |
| `control_test` | `{16,17}{42,6}{88,40}{164,16}` | **변경 없음** | 79B |
| `project` | `{16,17}{48,22}{86,42}` | **변경 없음** | 81B |

메모는 diag 를 `{0,16}` 으로 적었으나 **`{0,33}` 으로 간다** (사용자 확정). `{0,16}` 이면
SYS(16:17)가 빠지고, 그러면 04 §2.3 변경 1 — *"모든 프리셋이 SYS 전체를 읽는다"* — 이
무너진다. 그 규칙은 `NodeStatus` 매핑(03 §5.3)이 보드·모드 분기 없이 성립하는 근거이고,
어긴 결과가 **엔코더 버스 100% degraded 를 몇 주 동안 못 본 사고**(06 §10 B1)다.
`{0,16}` 과 `{16,17}` 은 인접하므로 합쳐도 세그먼트가 늘지 않는다.

`{188,4}` 는 신규다 — `auto_mode`(188) · `soft_estop`(189) · `mode`(190) · `use_lpf`(191).
TAB3 버튼 4종의 리드백 소스이고, diag 프리셋에서만 실값이 된다.

`{224,16}` 은 DIAG 32B 중 앞 16B다. DIAG 는 `cmd_write_tick`(u32) + 28B 예약이므로
**의미 있는 것은 앞 4B 뿐**이고, 뒤 16B 를 안 읽어도 잃는 정보가 없다.

### 1.2 리드백 20B 폐지 — 파급 세 곳

메모의 문제 제기가 이것이다:

> CMD_Motor 쪽의 리드백을 왜 받아야 하는거야??? 이미 write를 실패하면 access에러 나오니까
> shadow 값을 이전 값으로 회귀 시키면되지 않을까. 20바이트면 너무 낭비인거 같아

맞다. 그런데 **섀도가 곧 write 버퍼**라는 구조 때문에 (`rd_control.cpp:310` — `PrepareWrite`
가 `shadow_->ecu.reg.cmd_motor` 에 직접 쓰고, 슬롯이 그 구간을 그대로 wire 로 보낸다)
리드백을 빼면 세 곳의 의미가 바뀐다. 하나씩 처리한다.

#### ① `OP_SET_CTR_MODE` 검증 — **없앤다** (확정)

`DoInSpanCtrMode` (`rd_control_api.cpp:104`) 는 write 후 10 tick 동안
`state_->ecu.reg.cmd_motor.ctr_mode[i]` 가 목표값이 되는지 본다. 리드백이 있을 때는 그것이
**ECU 가 실제로 받아들였는가**였지만, 없으면 브리지가 자기가 쓴 값을 다시 읽는 꼴이라
**무조건 1 tick 만에 통과한다.** 통과하는 검증은 검증이 아니라 거짓 보증이다.

→ 검증 루프를 제거하고, 응답 메시지에 **검증하지 않았다는 사실을 명시한다.**
`"ctr_mode = N 설정 (섀도 반영 — 리드백 없음, 미검증)"`. 조용히 지우면 종전에 "검증 OK
(3 tick)" 를 보던 사람이 같은 문장이 없어진 것을 못 알아챈다.

> **왜 응답 err 기반으로 대체하지 않았나**: ctr_mode 는 in-span 이라 자기 전용 트랜잭션이
> 없다. 다음 RW tick 의 err 는 *그 tick 의 write 구간 전체*에 대한 것이라 ctr_mode 만
> 골라낼 수 없다. 반쪽 신호로 "검증했다" 고 말하는 것이 아무 말도 안 하는 것보다 나쁘다.

#### ② `ControlFeedback.cmd` — 의미가 **"ECU 가 받은 값" → "브리지가 보낸 값"** 으로 바뀐다

`rd_telemetry.cpp:355` 는 `reg.cmd_motor.cmd_{current,velocity,position}` 을 싣는다.
이것은 섀도이므로, `{164,16}` 리드백이 없으면 자동으로 **브리지가 마지막으로 쓴 값**이 된다.
코드는 한 줄도 안 바뀌지만 **필드의 의미가 바뀌므로 주석·문서에 못 박는다.**

`control_test`(auto_mode:none)에서는 브리지가 아무것도 쓰지 않고 `{164,16}` 리드백이
살아 있으므로 **거기서는 여전히 ECU 실값**이다 — 같은 필드가 프리셋에 따라 다른 것을
뜻한다. 이 비대칭이 이번 결정의 대가이고, 숨기지 말고 적어 둔다.

#### ③ 쓰기 실패 시 **섀도 롤백** — 신규

메모가 리드백의 대안으로 제시한 것. 지금은 WRITE 응답의 err 를 확인만 하고 섀도는
그대로 둔다. err ≠ 0 이면 **ECU 는 안 받았는데 섀도는 받은 것처럼 남아 있고**, 그 값이
그대로 텔레메트리로 나간다 (②에서 `cmd` 의 의미가 "보낸 값" 이 된 이상 더 중요해진다).

> ### ⚠ 원안 정정 (2026-08-05, U2 구현 중)
>
> 이 절은 원래 *"wire 로 내기 **직전에 그 구간을 스냅샷**하고, err ≠ 0 이면 되돌린다"* 고
> 적었다. **그 스냅샷은 되돌릴 값이 아니다.** 순서가 이렇기 때문이다:
>
> ```
> ① 누군가(PrepareWrite / 서비스 콜백)가 섀도에 새 의도값 V 를 쓴다
> ② Encode 가 섀도에서 V 를 읽어 패킷에 담는다        ← 원안의 "직전 스냅샷" = V
> ③ ECU 가 거부한다
> ④ 되돌려야 할 값은 직전에 ECU 가 받아들인 V_prev 인데, ②의 스냅샷은 V 다
> ```
>
> 즉 원안대로 하면 **V 를 V 로 덮는 no-op** 이다. 섀도는 "쓰기 버퍼" 이므로 이전 값이
> 이미 지워져 있고, 되돌리려면 **따로 들고 있어야 한다.**

**확정 메커니즘 — 마지막으로 수락된 바이트의 거울(`WriteEcho`).**

노드마다 `accepted[256]` + `valid[256]` 을 둔다 (`sched/rd_write_echo.hpp`).

| 응답 | 처리 |
|---|---|
| **ACCEPTED** (err 니블 = 0) | 보낸 바이트를 거울에 새긴다 — 다음 되돌림의 기준점 |
| **REJECTED** (err 니블 ≠ 0) | 섀도를 거울로 되돌린다. **수락 이력이 있는 바이트만** |
| **UNKNOWN** (무응답·형식 오류) | **아무것도 하지 않는다** |

세 가지가 이 설계의 요점이다:

- **`valid` 마스크가 필요하다.** 기동 직후에는 수락된 값이 없다. 그때 거부가 나면 되돌릴
  대상이 0 으로 초기화된 거울인데, 그 0 을 섀도에 쓰면 *"ECU 가 0 을 갖고 있다"* 는
  **거짓말을 새로 만든다.** 이력이 없으면 손대지 않는다.
- **UNKNOWN ≠ REJECTED.** 무응답은 "보드가 못 받았다" 가 아니라 **"받았는지 모른다"** 다 —
  요청은 나갔고 응답만 유실됐을 수 있다. 모르는 것을 되돌리면 실제로 적용된 값을 지운다.
- **같은 트랜잭션의 읽기 구간은 되돌리지 않는다.** RW 는 쓰기가 거부돼도(`wr_err≠0`) 읽기는
  성공할 수 있고(`rd_err=0`), 그러면 Decode 가 방금 **ECU 실값**을 섀도에 넣은 상태다.
  거기를 거울로 덮으면 되돌림이 오히려 진실을 지운다. 겹침은 실제로 생긴다 —
  diag 프리셋은 `{128,4}` 를 읽고 `auto_mode=direct` 는 `128:52` 를 쓴다.

> ⚠ **200Hz 제어 경로에서 롤백의 실익은 제한적이다** — 다음 tick 이 어차피 새 값을 덮는다.
> 실익은 `ctr_mode`·`motor_mask` 같은 **한 번 쓰고 유지되는 값**과, 거부가 지속될 때
> `ControlFeedback.cmd` 가 ECU 실상태를 반영하는 데 있다. 이 기능의 목적은
> "제어를 복구한다" 가 아니라 **"섀도가 ECU 에 대해 거짓말하지 않게 한다"** 이다.

> | 120·121 | dpca locker_en·boot_en | (Step 7 TODO — 아직 분배 안 함) | 값은 남는다 |
> | 122·123·124·125 | locker_en·boot_en·light_en·servo_cmd | **매 사이클 무조건 적용** | ✅ |
> | 126 | mode | 소비 후 **0xFF 로 되돌림** (트리거) | ❌ |
> | 127 | sys_state_target | 〃 | ❌ |
>
> 126·127 은 "쓰면 소비되고 사라지는" 트리거라 읽으면 항상 0xFF 다. 게다가
> **`DPC_CTL.MODE` 를 발행하는 R/O 필드가 레지스터 맵에 아예 없다.**
> 127 의 실제 상태는 `sys_state`(57)로 간접 확인되지만, **126 은 관측 경로가 없다.**
>
> 그래도 `{120,8}` 을 통째로 읽는다 — 5B 를 위해 세그를 쪼개면 wire 헤더가 더 든다.

DPC-B 는 멀티세그 READ 를 받는다 (2026-08-03 실기: 16+8+37 = 61B ✓). 세그 2개는 안전하다.

## 3. `rd_sequence` — 진입 게이트

메모의 규칙:

```
1. DPC_STATE_CHECK :  READ  (1)HOLD Check 후
2. DPC_DEPLOY:        WRITE (2)INIT
3. DPC_WAIT_CAMERA:   READ  (5)WAIT Check 후
4. CAMERA_ACTION:     TODO
5. DPC_RETRACT:       WRITE (6)ASCEND_1
6. DPC_WAIT_RETRACT:  READ  (8)FINISH
```

2~6 은 **현행 구현과 이미 일치한다** (READ 판정은 주기 갱신된 섀도의 57번, WRITE 판정은
응답 성공). 실제 변경은 1단계뿐이다.

### 3.1 HOLD 를 **거칠 필요가 없다** — 펌웨어 확인 결과 (2026-08-05)

초안은 `CTRL → target=HOLD → HOLD 도달 대기 → INIT` 을 넣으려 했다. **DPC 펌웨어를 읽어
보니 불필요하다.** `rd_map_dpcb.c:264`:

```c
if(reg.cmd_dpcb.sys_state_target != 0xff){
    DPC_CTL.STATE = reg.cmd_dpcb.sys_state_target;   /* 검증도 마스크도 없다 */
    reg.cmd_dpcb.sys_state_target = 0xff;
}
```

**현재 상태와 무관하게 그냥 대입한다.** 전이 가드가 펌웨어에 없으므로 CTRL(0)에서 INIT(2)을
쓰는 것과 HOLD(1)에서 쓰는 것이 **바이트 단위로 같은 일**이다 (DPC 제작자 확인과 일치).

> 이것은 동시에 **왜 Orin 쪽 `IsWritableTarget()` 가드가 필요한가**의 근거이기도 하다.
> 펌웨어가 아무 값이나 받으므로 `DESCEND_2`(4) 같은 중간 상태를 실수로 쓰면 **FSM 단계를
> 통째로 건너뛴다.** 막는 주체는 Orin 밖에 없다.

### 3.2 진짜 전제조건은 `mode == AUTO(1)` 이다 ★

`RD_CONTROL_LOOP` 의 FSM `switch` 는 **`CTL->MODE == 1` 일 때만 돈다** (`rd_control.c:111`).
MANUAL(0)이면 `RD_CONTROL_CASE_IDLE` 만 돌고 `STATE` 는 읽히지도 않는다.
그리고 `MODE` 는 **부팅 기본값이 0(MANUAL)** 이다 (`rd_control.c:58`).

여기에 함정이 겹친다 — `reg.sys.sys_state`(57)는 `DPC_CTL.STATE` 를 **그대로 복사해서
발행한다** (`rd_map_dpcb.c:184`). 즉:

> **MANUAL 에서 127에 2를 쓰면 `sys_state` 가 2로 읽히는데 아무것도 안 움직인다.**
> 시퀀스는 그것을 "전개 중" 으로 보고 WAIT(5)를 30초 기다리다 타임아웃 Abort 한다.
> 관측값(2)이 정상 진행과 완전히 같아 **증상만으로는 원인을 알 수 없다.**

`mode`(126)는 **읽을 수 없다** (§5.3 참조) — "확인 후 진행" 이라는 선택지가 없다.
쓰거나 안 쓰거나뿐이고, **확정: 시퀀스가 `mode=AUTO` 를 먼저 쓴다.**

### 3.3 확정 전이

```
DPC_STATE_CHECK ─ sys_state ∈ {CTRL(0), HOLD(1)} ─ 126=AUTO(1) write ─▶ DPC_SET_AUTO
                ├ ERROR(10) ─▶ Abort
                └ 전개 FSM(2~8) ─▶ Abort ("이전 시퀀스가 안 끝났다")

DPC_SET_AUTO ─ write 응답 성공 ─ 127=INIT(2) write ─▶ DPC_DEPLOY ─▶ (이하 기존과 동일)
```

`Seq` 에 `DPC_SET_AUTO` 한 칸이 는다 (초안의 `DPC_WAIT_HOLD` 를 대체한다 — 기다릴 상태가
없으므로 write 완료만 본다). 타임아웃은 기존 `kWaitTicksMax`(5Hz × 150 = 30s).

**조작자가 패널로 고른 MANUAL 을 Orin 이 덮어쓴다**는 것이 이 결정의 대가다. 로그에
남기고, TAB3 의 mode 버튼 표시도 전개 후 AUTO 로 갱신한다.

### 3.4 유지하는 것

`DPC_WAIT_RETRACT` 가 `FINISH(8)` 과 `CTRL(0)` 을 **둘 다 완료로 받는 것은 유지한다** —
5Hz 폴링으로는 FINISH 를 스쳐 지나갈 수 있고, 하나만 보면 이미 끝난 시퀀스를 타임아웃
실패로 처리하게 된다. 메모가 FINISH 만 적은 것은 표기이지 게이트 축소가 아니다.

ESTOP_SET / ESTOP_RELEASE 도 유지한다 (메모는 DPC 구간만 다뤘다).
`CAMERA_ACTION` 은 TODO 로 남긴다 — 카메라 미연결.

### 3.5 ⚠ 선행 조건 — `RD_MAP_MARSHAL_CONSUME` 이 호출되지 않는다

`stm_ws/DPC_B/Core/Src/rd_system.c:351`:

```c
RD_MAP_MARSHAL_PUBLISH(&DPCB_PERIPHERAL);
//RD_MAP_MARSHAL_CONSUME(&DPCB_PERIPHERAL);      ← 유일한 호출부
```

**주석 처리돼 있다.** 커밋 `9ba1228`(2026-08-04)에서 *처음부터 주석인 채로* 추가됐고 —
풀린 적이 없다. 즉 **지금 Orin 이 120~142 어디에 무엇을 쓰든 DPC 는 반응하지 않는다.**
섀도만 바뀌고 끝난다.

이 계획의 **§3 시퀀스 전체 · §5.3 DPC 버튼 5종 · §5.3 ④ jeongae UI 가 전부 이것 위에 선다.**
Orin 쪽은 정상 동작해도 실기에서는 아무 일도 일어나지 않고, `sys_state` 로도 판별되지
않는다(§3.2와 같은 이유).

**범위 밖 — 사용자가 STM32CubeIDE 에서 따로 처리한다** (사용자 결정, 2026-08-05).
Orin 쪽 단위(U5·U11·U12)의 **실기 검증은 이것이 풀린 뒤에만 의미가 있다.** 빌드·유닛
테스트는 무관하게 진행한다.

## 4. 보드별 읽기 on/off

메모의 "각 보드의 On / off 상태 감지" 와, 브리지 기동에서 보드를 골라 켜는 것 둘 다.

### 4.1 `enable_ecu_read` 신설

지금은 `enable_dpc_read` · `enable_pcu_read` 만 있고 (기본 false, `rd_schedule.cpp:531-532`
에서 슬롯을 skip) ECU 는 항상 켜져 있다. 세 보드를 대칭으로 만든다.

> ⚠ **project 프레임 10칸 중 5칸이 ECU RW 다** (cmd_vel WRITE + 센서 READ 한 트랜잭션).
> ECU 를 끄면 **주행 제어가 통째로 사라진다.** DPC 단독 시험용이며, 꺼진 상태는 기동
> 로그와 웹 상단에 **경고로 표시한다** — 조용히 꺼져 있으면 "왜 안 움직이지" 가 된다.
> `enable_ecu_read` 기본값은 **true** 다 (나머지 둘은 false 유지).

### 4.3 project INIT + `active_motors` 빈칸 (2026-08-05 확정)

§0.3 이 드러낸 "project 는 INIT 이 없다" 를 메운다. 사용자 지시:
*"project 에서도 init 이 가능해야 하고, auto 는 물론, active motor 설정도 가능하게."*

**project INIT** — `InitProject()`. control 과 **다른 것은 auto_mode 하나뿐**이다.

| 단계 | control | project |
|---|---|---|
| ① motor_mask(192) | 파라미터 값 write+검증 | 같음 (빈칸이면 READ 채택 — 아래) |
| ② auto_mode(188) | 파라미터 값 (`none` 제외) | **KINEMATIC(0) 고정** |
| ③ mode(190) | AUTO | 같음 |

②가 갈리는 이유: project 는 `cmd_lin_vel`/`cmd_ang_vel`(180:8)을 쓰고 **바퀴 분배는 ECU 가**
한다 — 그 경로가 KINEMATIC 이다. control 에서는 금지된 값인데(ECU 가 100Hz 로 ctr_mode 를
덮어써 bridge 의 cmd_motor write 와 경쟁) project 는 cmd_motor 를 아예 안 쓰므로 경쟁 상대가
없다. 따라서 기동 파라미터 `auto_mode` 는 **project 에서 무시**되며, 무시했다는 사실을 로그로
알린다 (조용히 무시하면 "current 로 띄웠는데 왜 KINEMATIC 이지" 가 된다).

INIT 뒤에 `MarkInitDone()` + `on_init_done_(false)` 를 부른다 — 이걸 빼면 §0.3 의 ②③
(FSM 이 INIT 에 갇히고 config 서비스가 안 열림)이 그대로 남는다. `with_profiles=false` 인
이유는 project 의 write 가 cmd_vel 이고 프로파일 재생 대상(cmd_motor)이 아니기 때문이다.

**`active_motors` 빈칸 = "건드리지 않는다"**

메모: *"빈칸으로 작성 시에는 active motor 명령 안보냄 (기존 값 그대로 진행)"*.
종전에는 빈 값이 **기동 거부**였다("구동할 모터가 없다"). 뒤집는다 — 조작자가 빈칸을 넣은
것은 오타가 아니라 의도 표명이다.

- 빈칸이면 motor_mask WRITE 를 **건너뛰고**, INIT 이 addr192 를 **READ 해서 채택**한다
  (`AdoptMotorMask`). 읽지 않으면 `cfg_.active_motor_mask` 의 초기값 `0x0F` 가 그대로
  `GET_STATUS` 로 나가 **관측이 아닌 추측이 실값처럼 보인다.**
  (어느 읽기 프리셋도 192 를 읽지 않으므로 여기서 한 번 명시적으로 읽어야 한다.)
- 채택값이 0 이면 "어떤 트랙도 안 돈다" 를 경고한다. 기동을 막지는 않는다.
- 범위 밖 값(`[0]`·`[5]`)은 **여전히 거부**다 — 빈칸 허용이 "아무 값이나 허용" 으로
  번지지 않게 한다.

> ### ⚠ 빈칸의 표기는 `""` 다. `[]` 가 **아니다** (실측)
>
> 계획 초안(§5.1)은 `[]` 또는 "파라미터 생략" 으로 적었으나 둘 다 안 된다:
>
> - **`[]`** — 빈 배열은 원소 타입 추론이 안 돼 override 가 `NOT_SET` 으로 들어오고,
>   ROS 2 Humble 이 **노드 생성 단계에서 terminate 한다.** 파라미터 이름과 무관하며
>   (선언하지 않은 이름으로도 죽는다) try/catch 로도 못 막는다.
> - **생략** — 그러면 control 의 기본 동작(`[1,2,3,4]` write)이 바뀐다.
>
> → **빈 문자열**(`-p active_motors:=""`)을 빈칸으로 삼는다. dynamic typing 으로 받아
>   `PARAMETER_STRING` + empty 를 빈칸으로 해석한다.
>
> ⚠ **셸 인용 주의**: 셸에 `-p active_motors:=""` 를 그대로 주면 따옴표가 벗겨져
>   `-p active_motors:=` 가 되고 **rcl 이 노드를 죽인다**. 홑따옴표로 감쌀 것:
>   `-p 'active_motors:=""'`. 웹 감독자는 `subprocess` 리스트로 넘겨 셸을 안 거치므로 무관하다.

### 4.2 보드 연결 상태를 `GET_STATUS` 로 노출

`StatusToJson` 에 `nodes` 키를 추가한다. 지금 스키마에는 보드별 연결 여부가 **없어서**
웹이 "DPC 가 붙어 있나" 를 물을 방법이 없다.

```json
"nodes": {
  "ecu": {"enabled": true,  "connected": true,  "fail_streak": 0},
  "dpc": {"enabled": true,  "connected": false, "fail_streak": 585},
  "pcu": {"enabled": false, "connected": false, "fail_streak": 0}
}
```

> **정정 (2026-08-06 구현 중)**: 초안의 `last_ok_s`(초) 대신 **`fail_streak`**(마지막 성공
> 이후 연속 실패 트랜잭션 수) 을 낸다. `CommHealth_t` 에 타임스탬프가 없어 초 단위를
> 만들려면 **L0(`rd_map`)에 시계를 주입**해야 하는데, 이미 있는 `timeout_cnt` 가 같은
> 질문에 답한다.

`enabled`(설정) 와 `connected`(관측)를 **분리해서 낸다.** 합치면 "안 켰다" 와 "켰는데
대답이 없다" 가 같은 화면이 되고, 그 둘은 조작자에게 완전히 다른 상황이다.

| DPC | 126 | DPC mode | MANUAL(0) / AUTO(1) | 〃 |
| DPC | 127 | BOT deploy seq | 0~8 입력 | 〃 |

> ECU 190 은 **새 명령을 만들지 않는다.** `ControlConfig` 에 `OP_SET_MODE`(reg190,
> out-of-span, IDLE 전용)가 이미 있고, 거기에는 in/out-of-span 처리와 IDLE 게이트가 붙어
> 있다. 같은 이름을 카탈로그에도 만들면 **auto_mode 를 바꾸는 길이 둘이 되고 게이트가
> 다르다** — `rd_command_catalog.hpp:19` 가 명시적으로 거부한 형태다.

**③ 버튼 상태 동기화** — 탭 진입 시 전체 읽기 1회로 초기 세팅, 이후 Write 성공 시 스위칭.
**리드백이 되는 버튼과 안 되는 버튼을 화면에서 구분한다** — 안 되는 것을 되는 것처럼
그리면 마지막 전송값이 실제 상태로 읽힌다.

| 버튼 | 동기화 소스 | 표시 |
|---|---|---|
| DPC 123 boot / 124 light / 125 mount | `{120,8}` 20Hz 리드백 (§2) | 실값 — **패널 조작도 따라온다** |
| DPC 126 mode | ~~**없음** (0xFF만 읽히고)~~ → **에코된다** | 에코값 + `반영 확인 없음` 배지 |
| DPC 127 seq | 에코 + `sys_state`(57) 20Hz | **둘 다** 보여 준다 (다를 수 있고, 그 차이가 정보다) |
| ECU 189 / 190 / 191 | `diag` 프리셋의 `{188,4}` 뿐 | project 에서는 낙관적 스위칭 + 같은 배지 |

126 은 §3.3 에서 **시퀀스가 전개 시작 시 AUTO 로 덮어쓴다** — 그때 화면 표시도 갱신한다.

> ⚠ **위 표 두 줄을 2026-08-06 실측으로 정정했다 (U11).** *"126 은 0xFF 만 읽힌다"* 는
> 틀렸다 — DPC CMD 영역(123~127)은 **전부 쓴 값이 그대로 에코된다.** 확인 방법: 124 에 1 을
> 쓰고 126 에 1 을 쓴 뒤 `OP_GET_REGISTERS` → 둘 다 0x01 로 읽힌다. (그전에 전부 0 이라
> "0 이 읽혔다" 만으로는 판별이 안 됐다 — 0 은 기본값이다.)
>
> 그래서 배지의 의미가 바뀐다. 없는 것은 **리드백**이 아니라 **반영 확인**이다:
> 지금 DPC 펌웨어의 `RD_MAP_MARSHAL_CONSUME` 이 주석 처리돼 있어 **DPC 는 바이트를
> 저장만 하고 아무것도 하지 않는다.** 에코는 완벽한데 솔레노이드는 안 움직인다.
> 에코를 초록불로 그리면 이 상태가 화면에서 "정상 동작" 이 된다 — 이 프로젝트가 반복해서
> 지워 온 결함 형태가 정확히 그것이다.
>
> → 화면은 **수신(에코)** 과 **반영** 을 다른 열로 그린다. 독립 관측이 있는 것은 둘뿐이다:
> `127 → sys_state(57)` · `122 locker → lock_contact(66)`. 나머지는 되먹임 선이 없다.

**④ jeongae 자동 전개** (확정 — 넣는다)
`[자동 전개 시작]` · `[lock 해제]` 버튼 + 현재 `Seq` 단계 · 경과 tick 표시.
수동 127 입력과 **배타**로 잠근다 — 시퀀스가 `IDLE` 이 아니면 127 입력칸을 막는다.
겹쳐 쓰면 시퀀스가 자기가 안 쓴 상태 전이를 보고 Abort 한다.
`Trigger`/`SetLock` 을 웹에서 부를 경로가 필요하다 (현재는 `/carrier/jeongae` 토픽뿐).

### 5.4 TAB4 — 레지스터 (구 TAB3, Advanced)

**① 실시간 반영 — 섀도 폴링 10Hz + 기동 전체읽기** (확정)

`OP_GET_REGISTERS` 는 **버스를 안 건드린다** — 브리지 섀도를 덤프할 뿐이다. 그래서 웹이
10Hz 로 폴링해도 통신 부하가 0 이다. 지금 화면이 안 움직이는 이유는 폴링을 안 해서다
(`[전체 읽기]` 버튼 또는 2초 자동 체크박스).

문제의 나머지 절반은 **섀도의 어느 부분이 실제로 갱신되느냐**다. 주기 슬롯이 읽는 구간만
살아 있고 나머지는 기동 이후 한 번도 안 채워진다.

→ 브리지 INIT 에서 **각 활성 보드의 전 구간을 1회 읽어 섀도를 채운다.**
ECU 는 `cmdcat::spans::kAll`(216B, 예약 제외)로 한 트랜잭션. DPC 도 같은 방식으로
예약 구간을 뺀 전 구간 프리셋을 만든다.

→ 화면은 신선/미판독 2값이 아니라 **경과시간(age)** 을 보여 준다. 기동 스냅샷은
"읽긴 읽었는데 30초 전 값" 이고, 그건 신선도 이분법으로 표현되지 않는다.
`fresh` 구간 밖 · 한 번도 안 읽힌 자리는 지금처럼 회색 미판독 유지.

**② raw 명령을 전 모드에서 허용** (확정 — B6 정책 변경)

지금 `CMD_RAW_READ`/`CMD_RAW_WRITE` 는 `manual_only=true` 라 project·control 에서 거부된다
(`rd_command_catalog.hpp:168`). **TAB4 는 Advanced 탭이므로 직접 편집이 되어야 한다.**

→ `manual_only` 게이트를 raw 에서 해제한다. 03 §7.2 (c) 의 *"raw 는 manual 전용"* 이
이번에 뒤집힌다. **tick 훔치기는 그대로다** — control 은 프레임당 1칸(최대 5Hz),
project 는 전용 슬롯 3칸. 스케줄 층의 상한은 손대지 않는다.

> **남기는 게이트**: `CMD_RAW_WRITE` 의 `needs_safe_stop` 은 유지한다. 달리는 중에 임의
> 주소를 쓰는 것은 모드와 무관하게 막아야 한다. 화면에 *"이 탭의 쓰기는 정지 상태에서만"*
> 을 명시한다. `manual_only` 를 여는 것과 `needs_safe_stop` 을 여는 것은 다른 결정이다.

**③ DPC 레지스터 맵 추가** (PCU 는 보류)

`www/regmap.json` 은 ECU 전용이다. target 별로 나누고 DPC 맵을 `rd_register_dpc.hpp` 기준
으로 추가한다. **`test_regmap.py` 의 헤더 대조도 같이 확장한다** — 손으로 옮겨 적은 표는
반드시 갈라지고, 이 프로젝트에서 이미 세 번 겪었다 (07 §5.1).
PCU 는 레지스터 미확정이라 선택지에 자리만 두고 비활성.

**④ `regmap.js` 의 `TARGET.dpc` 를 210 → 209 로** (§0.2 — ID 변경 누락분).

## 6. 명령 카탈로그에 target 축 추가

§5.3 의 DPC 버튼 5종을 보내려면 카탈로그가 **ECU 주소 전용**인 것을 풀어야 한다.
`CmdDef.waddr` 하나로는 "DPC 의 124번" 을 표현할 수 없고, 지금 `CmdKind::READ` 는
`req.target_id != ECU` 를 아예 거부한다 (`rd_command.cpp:70`).

```cpp
struct CmdDef {
    uint8_t     cmd;
    const char* name;
    CmdKind     kind;
    uint8_t     target;        // ← 신규. TARGET::ECU / DPC / PCU / ANY(raw)
    const ReadPreset* read;
    uint16_t    waddr;
    bool        manual_only;   // ← raw 에서 false 로 (§5.4 ②)
    bool        needs_safe_stop;
};
```

신규 명령 (번호는 03 §7.3 의 미사용 대역에서 잇는다):

| cmd | 이름 | target | addr | 값 |
|---|---|---|---|---|
| 40 | `dpc_set_boot` | DPC | 123 | 0/1 |
| 41 | `dpc_set_light` | DPC | 124 | 0/1 |
| 42 | `dpc_set_servo` | DPC | 125 | 0/1/2 |
| 43 | `dpc_set_mode` | DPC | 126 | 0/1 |
| 44 | `dpc_set_seq` | DPC | 127 | 0~8, `IsWritableTarget()` 통과값만 |
| 45 | `dpc_read_all` | DPC | — | 예약 제외 전 구간 (TAB4 기동 읽기) |

`dpc_set_seq` 는 **`dpc::IsWritableTarget()` 을 그대로 쓴다** (CTRL/HOLD/INIT/ASCEND_1 만).
메모는 "0~8 입력 가능" 이라 적었지만 FSM 중간 상태를 밖에서 쓰면 단계를 건너뛴다 —
`rd_sequence.cpp:18` 이 이미 같은 이유로 막고 있고, 두 경로가 다른 규칙을 쓰면 안 된다.
UI 는 허용값만 버튼으로 내고, 나머지는 회색으로 *왜 못 쓰는지*를 보여 준다.

`req.target_id` 와 `def->target` 이 다르면 거부한다 — 표에 적힌 대상이 곧 계약이다.

## 8. 범위 밖 / 보류

- **TAB4 Reboot 이 안 들어가는 문제** — 원인 미규명(카탈로그상 `needs_safe_stop=true` 라
  정지 상태가 아니면 거부되고, 사유는 화면 하단 notice 에만 뜬다). **사용자 지시로 이번
  단계 제외.** 다음에 볼 때 확인 순서: ① 거부 메시지가 실제로 뜨는가 ② 슬롯은 잡히는데
  응답이 없는가 ③ STM 이 재부팅을 안 하는가.
- **PCU** — 레지스터 미확정 (04 §6). 자리만 두고 비활성.
- **`realtime_tick` 단위 주석** — DPC 는 `[ms]` 표기가 약 1000× 틀렸으나 heartbeat 용도로
  확정돼 무해하다 (plan_260803 §4.5). 편할 때 주석만 정정.
- **Q3 슬롯 10칸 재편의 잔여**, 02 §4 디렉터리 계층, 01 §8.1 심볼 개명 — 기능 영향 없음.
- **STM 펌웨어** — 이번 계획은 Orin 쪽만이다. 통신 계층은 이미 필요한 것(멀티세그 READ,
  버퍼 256/272)을 갖고 있다. 단 **`RD_MAP_MARSHAL_CONSUME` 주석 해제는 선행 조건이다**
  (§3.5) — 사용자가 따로 처리한다.
- **DPC `mode`(126) 리드백** — R/O 발행 필드가 레지스터 맵에 없어 관측이 불가능하다.
  이번엔 "쓰기만 하고 확인 안 함" 으로 간다. 나중에 `SYS` 블록(46~61)에 R/O `sys_mode` 를
  추가하면 시퀀스가 진짜로 *확인 후 진행* 할 수 있게 되고 TAB3 버튼도 실값이 된다.
  **STM 레지스터 맵 변경 + Orin 미러 갱신**이 따르므로 별건으로 둔다.
- **`sys_state`(57) 헤더 주석** — `rd_register_dpcb.h:157` 이 *"발행 소스
  payload_state→DPC_CTL.STATE 교체는 별도 TODO(현재 미반영)"* 라고 적고 있으나 실제
  코드(`rd_map_dpcb.c:184`)는 이미 `DPC_CTL.STATE` 를 쓴다 — **주석이 낡았다.** 사소.

## 9. 검증 원칙

- **회귀는 구 코드에 대고 실패를 먼저 본다.** "고쳤더니 통과한다" 는 애초에 안 깨져 있었을
  때도 똑같이 보인다.
- **관측값이 기본값과 같으면 판별 불가.** 예: 롤백 검증을 `cmd_current == 0` 으로 하면
  "롤백됨" 과 "원래 0" 이 구분되지 않는다 — 0 이 아닌 값을 쓴 뒤 실패시켜야 한다.
- 빌드: `orin_ws` **루트에서** `colcon build` → `colcon test` → `colcon test-result --verbose`.
- **실기 브리지를 띄운 채 `colcon test` 를 돌리지 않는다** — `InventoryTest` 가 같은 ROS
  그래프의 실행 중 브리지를 보고 실패한다. 코드 회귀가 아니다.
- 실기 검증은 **사용자 승인 후**에만.
