## U2 — 쓰기 실패 시 섀도 롤백

**목적**: `09_plan §1.2 ③`. err ≠ 0 인데 섀도가 성공한 척 남는 것을 없앤다.

**파일**
- `src/sched/rd_schedule.cpp` — WRITE / RW 슬롯 실행 경로.
  wire 로 내기 직전 write 구간(`s.write.addr`, `MaxLen()` ≤ 52B)을 스택 버퍼에 스냅샷,
  응답 `err != 0` 이면 `state_->ecu.reg` 의 같은 구간에 되돌린다.
- 롤백 발생 시 **rate-limited 경고 로그** (200Hz 에서 매 tick 찍으면 로그가 덮인다).

**검증**
- **회귀는 실패를 먼저 본다**: 주소를 일부러 잠근 상태(DEFINE `sys_write_mode=LOCK`)로
  WRITE 를 내고 err 를 받게 한 뒤, 구 코드에서 섀도가 새 값으로 남는 것을 확인 → 수정 후
  이전 값으로 돌아오는지 확인.
- **0 이 아닌 값으로 시험한다.** `cmd_current=0` 으로 하면 "롤백됨" 과 "원래 0" 이
  구분되지 않는다 (`verification-traps`).
- 유닛: 롤백 로직을 순수 함수로 빼서 (`이전값, 새값, err → 최종값`) 조합 고정.

## U5 — `rd_sequence` 진입 게이트

**목적**: `09_plan §3`. HOLD 경유는 **불필요**하다 (펌웨어에 전이 가드가 없다 — §3.1).
실제로 필요한 것은 `mode=AUTO` 선행 write 다 (§3.2).

**파일**
- `include/orin_firmware_bridge/policy/rd_sequence.hpp`
  - `Seq` 에 **`DPC_SET_AUTO`** 추가 (초안의 `DPC_WAIT_HOLD` 를 대체한다 — 기다릴 상태가
    없으므로 write 완료만 본다), `SeqName` 갱신, 전이도 주석 갱신.
- `src/policy/rd_sequence.cpp`
  - `DPC_STATE_CHECK`: `sys_state ∈ {CTRL(0), HOLD(1)}` → `126=MODE_AUTO` write 후
    `DPC_SET_AUTO` / `ERROR(10)` · 전개 FSM(2~8) → Abort.
  - `DPC_SET_AUTO`: `AutoCommandDone` 성공 → `PostDpcTargetLocked(STATE_INIT)` → `DPC_DEPLOY`.
  - `DPC_WAIT_RETRACT` 의 `also_ok = STATE_CTRL` 은 **그대로 둔다** (5Hz 폴링이 FINISH 를
    스쳐 지나간다 — 이유를 주석으로 재확인).
  - `PostDpcTargetLocked` 의 `IsWritableTarget()` 가드는 **더 중요해졌다** — 펌웨어가 값을
    검증 없이 대입하므로 중간 상태를 실수로 쓰면 FSM 단계를 통째로 건너뛴다. 주석에 근거를
    (`rd_map_dpcb.c:264`) 남긴다.
- 126 은 의미 명령(U6 의 `dpc_set_mode`)으로 보낸다 — 시퀀스가 raw 주소를 알 이유가 없다.
  **U6 선행**을 추가한다.

**검증**
- 유닛: `ISlotHost` 를 페이크로 물려 `DpcSysState` 를 CTRL/HOLD/ERROR/DESCEND_1 로 주면서
  전이 표를 고정. 미판독(`false` 반환) 케이스도 — 섀도 0 == `CTRL` 이라 값만으로는
  "안 읽음" 과 "정상 대기" 가 구분되지 않는다.
  `PostAutoWriteTo` 호출 인자를 페이크가 기록해 **126→127 순서**를 단언한다.
- 실기(**† STM 선행 조건**): CTRL 에서 트리거 → 126 write → 127 write → `sys_state` 가
  2→3→4→5 로 흐르는지.
  > ⚠ **`sys_state` 만으로는 성공을 판정할 수 없다.** MANUAL 이면 STATE 만 대입되고 FSM 은
  > 안 도는데 `sys_state` 는 똑같이 2 로 읽힌다 (§3.2). **모터가 실제로 움직이는지** 또는
  > `motor_data` present_position 변화를 같이 봐야 한다.

**설계에서 걸린 세 지점** (전부 테스트로 고정했다)

- **`valid` 마스크가 필요하다.** 기동 직후 거울은 0 인데 그 0 은 관측된 적 없는 값이다.
  되돌린다고 0 을 쓰면 *"ECU 가 0 을 갖고 있다"* 는 거짓말을 새로 만든다.
- **UNKNOWN ≠ REJECTED.** 무응답은 "못 받았다" 가 아니라 "모른다" — 요청은 나가고 응답만
  유실됐을 수 있다. 되돌리면 실제로 적용된 값을 지운다. `ClassifyWrite` 가 이걸 가른다.
- **같은 트랜잭션의 읽기 구간은 되돌리지 않는다.** RW 는 `wr_err≠0` 이어도 `rd_err=0` 일 수
  있고, 그러면 Decode 가 방금 ECU 실값을 넣은 상태다. 거기를 덮으면 되돌림이 진실을 지운다.
  겹침은 실재한다 — diag 는 `{128,4}` 를 읽고 `auto_mode=direct` 는 `128:52` 를 쓴다.

`Decode` 결과와 무관하게 반영을 먼저 하는 것도 같은 이유다 — read 에러로 조기 return 하면
그 tick 의 **수락**이 거울에 안 남아 다음 거부 때 낡은 값으로 되돌리게 된다.

> *"폴백이 걸려 READ 가 나가든 게이트가 안 먹어 RW 가 나가든 트랜잭션 수는 똑같이 1이라
> heartbeat 로는 판별할 수 없다."* 실제로 heartbeat 는 두 경우가 구분되지 않는다.

- `AbortsWhenModeAutoWriteFails` — mode 실패 시 전개 요청을 **내지 않는다.**

**두 조각이 왜 한 단위인가**

값만 채우면 30초 전 스냅샷이 실시간 값처럼 보이고, 나이만 주면 채울 값이 없다.

화면의 0 을 보고 "레지스터가 0" 인지 "안 읽어서 0" 인지 조작자가 판별할 수 없었다.

**바이트 단위로 둔 이유** — 구간 목록끼리 병합하려면 "겹치는 두 구간의 시각이 다를 때
어떻게 쪼개는가" 를 풀어야 한다. 그리고 **실제로 겹친다**: `kAll` 의 42:151 안에 control
프리셋의 48:80 이 들어 있다. 바이트마다 시각을 두면 그 문제가 사라지고, 스냅샷이 같은
(시각, 출처) 연속 바이트를 묶어 구간을 되만든다. 비용 7KB · 200Hz 경로에서 세그당 memset 1회.

**`ReadSrc` 가 아니라 `ReadOrigin`** — 슬롯 표에 이미 같은 이름의 다른 enum 이 있고
(그쪽은 "읽기 구간을 어디서 가져오는가": FIXED/PRESET) **둘 다 `PRESET` 을 갖는다.**
처음에 `ReadSrc` 로 썼다가 컴파일이 깨져서 알았다 — 컴파일러가 잡아 준 덕에 사람이
헷갈릴 자리가 하나 없어졌다.

**전체읽기를 모드 분기 *앞*에 둔 이유** (세 가지, `rd_schedule.cpp` 주석과 동일)

1. 네 분기(read_only_control·control·manual·project) 어디에나 필요하다. 분기 안에 넣으면
   네 번 적게 되고, 이 파일에서 그렇게 갈라진 것을 이미 여러 번 고쳤다.
2. INIT 의 write 보다 앞이라 **ECU 가 원래 갖고 있던 값**이 먼저 섀도에 들어온다.
   뒤에 두면 브리지가 방금 쓴 값을 다시 읽는 셈이라 기동 전 상태를 영영 못 본다.
3. `on_init_done_`(서비스 개방) 보다 앞이라 조작자가 화면을 열었을 때 이미 차 있다.

**실패해도 기동은 계속한다.** 표시용 스냅샷이지 제어의 전제조건이 아니다 — 여기서
노드를 죽이면 "레지스터 맵이 안 채워져서 주행을 못 한다" 가 되는데 목적과 정반대다.
재시도는 3회로 짧게 잡았다(`kFullReadMaxRetry`) — 보드 미장착 구성에서 10회 × 200ms 를
매번 기다릴 이유가 없다. PCU 는 레지스터 맵이 미확정이라 전 구간 프리셋 자체가 없다.

**`MarkRead` 가 RW 의 `start_addr` 을 안 찍는다** — 그건 **write 구간**이다. 찍으면
"쓴 것을 읽었다" 는 거짓이 되고, U2 에서 실제 결함이었던 것이 정확히 같은 혼동이다.
찍는 시점도 `Decode` **성공 뒤**다 — 실패한 읽기에 시각을 찍으면 화면이 낡은 값을
"방금 읽음" 으로 표시하는데, 그건 미판독보다 나쁘다.

**테스트 — 두 방향의 거짓을 막는다**

- `LaterReadWinsOnOverlap` — 이게 뒤집히면 기동 스냅샷이 주기 프리셋을 덮어 **신선한
  값이 낡아 보인다.** 42:151(init) 위에 48:80(preset)을 얹어 3칸으로 쪼개지는지 본다.
- `DisjointSegsStaySeparate` — 합치면 사이의 **미판독 구간이 읽힌 것으로 보인다.**
- `UnreadBytesAreAbsentNotZeroAge` — 미판독을 `age=-1`·`null` 같은 특수값으로 두지 않는다.
  특수값을 두면 소비자가 그것을 숫자로 읽는 경로가 반드시 생긴다.
- `OutOfRangeIsClamped` — 넘치면 옆 보드 배열을 침범한다. 침범 여부까지 같이 본다.
- `ReadAgeJson.*` 4개 — 키·타입·소수 자릿수. 종전 `fresh` 는 서비스 콜백 한가운데서
  조립돼 **어떤 테스트도 닿지 못했고**, 형식이 바뀌어도 웹을 띄우기 전엔 아무도 몰랐다.

#### ⚠ 별건 결함 ① — 대기 타임아웃이 30초가 아니라 **0.75초**였다

`kWaitTicksMax = 150` 옆에 *"5Hz tick 기준, 기본 30초"* 라고 적혀 있었다. **둘 다 틀렸다.**
`TickAutoSequence()` 호출부(`rd_schedule.cpp:658`, project/manual 분기)에 **레이트 분주가
없어** 200Hz 루프의 매 tick 마다 불린다 → 150 × 5ms ≈ **0.75초**.

DPC 가 정상 동작하더라도 **0.75초 안에 안 끝나는 전개는 무조건 Abort** 한다.

> **값을 보는 테스트로는 절대 못 잡는다.** `wait_ticks > max` 는 어느 주기에서든 참이고,
> 로그에는 "대기 초과" 만 남지 얼마 만에 걸렸는지는 안 남는다. **U12 가 `wait_ticks` 를
> `GET_STATUS` 로 꺼내 화면에 숫자를 띄우고 나서야 보였다.**

**→ 방법 A (사용자 결정) + 10초 (사용자 지정)**: 분주를 넣지 않고 상수를 고친다.
이 FSM 은 통신을 안 하고 상태 전이만 하므로 빨리 도는 것이 해롭지 않다.

```cpp
static constexpr uint32_t kTickHz       = 200;
static constexpr uint32_t kWaitTimeoutS = 10;
static constexpr uint32_t kWaitTicksMax = kTickHz * kWaitTimeoutS;   // 2000
```

**실측으로 확인**: `wait_ticks` 가 ~200/s 로 오르고(=200Hz 입증) **정확히 t=10.0s 에 만료**.

**설계 — `busy` 를 브리지가 준다**

웹이 `state !== 'IDLE'` 로 흉내내면 단계 이름이 하나 늘 때마다 웹도 같이 고쳐야 하고,
안 고치면 **새 단계에서 수동 127 입력이 열린 채로 남는다.** 그 상태로 쓰면 시퀀스가
자기가 안 쓴 상태 전이를 보고 Abort 한다. → `sequence.busy` 를 그대로 쓴다.
**`sequence` 를 모를 때는 잠근다** (모르면 안전측).

**트리거는 기존 `/jeongae` 토픽 그대로** — 브리지에 새 서비스를 파면 같은 동작에 입구가
둘이 되고 게이트가 갈라진다(03 §7.3 이 이미 거부한 형태). lock 검사는 `RdSequence` 안에
있어 어느 입구로 오든 같은 게이트를 받는다.

**검증**

- `ctest` **30/30** (신설 4 + status JSON 2) · `pytest` **81/81**
- 실기 (project + DPC, 모터 1번):
  - `GET_STATUS.sequence` = `{state, wait_ticks, wait_max:2000, busy, locked}`
  - 전 단계 흐름 — **U5 의 `DPC_SET_AUTO` 가 여기서 처음 실기 확인됐다**:
    `ESTOP_SET → DPC_STATE_CHECK(HOLD 통과) → DPC_SET_AUTO(126) → DPC_DEPLOY(127) →
     DPC_WAIT_CAMERA` → 10초 만료 → Abort
  - Abort 가 **soft ESTOP 을 되돌리고**(cmd_vel 재개) **lock 을 건다**(재트리거 차단)
  - lock ON/OFF 웹에서 동작 · lock 중 전개 시작 버튼 잠김
  - **배타 잠금 실기 확인**: `busy=true` 창에서 `pj-seq-val.disabled = true`
  - 정리 완료 — DPC 120:8 전부 0

**남은 것**: `DPC_WAIT_CAMERA` 를 통과하는 경로는 DPC 레지스터 구현이 끝나야 볼 수 있다.
지금은 무엇을 써도 `sys_state` 가 `HOLD(1)` 에 머물러 반드시 10초 만료로 끝난다.

⚠ 화면 갱신이 한 번 지연되는 것을 봤는데(단계 표시가 `IDLE` 로 머묾) **재현되지 않았다.**
인터벌·`render()` 호출은 계측으로 정상 확인했고(2.2초에 5회), 이후 시도에서는 즉시 갱신됐다.
브라우저 타이머 스로틀링으로 추정하지만 **확인하지 못했다.**

**⚠ 결함 하나 — 편집 전송이 항상 ECU 로 갔다**

`sendEdits()` 의 `target_id` 가 `TARGET.ecu` 로 박혀 있었다. 보드 선택을 붙이는 순간
**DPC 표를 띄우고 값을 고치면 같은 주소의 ECU 레지스터로 나간다.** 주소가 같아도 뜻이

이름이 그렇고, 후자는 ECU 전용 의미 명령 목록이라 화면에 `ECU 전용` 을 명기했다.

**age 표시 — U8 이 여기서 쓰인다**

종전 판정(`inFresh`)은 *"지금 주기적으로 읽히는가"* 여서, **기동 전체읽기로 채워진 구간이
값이 있는데도 '미판독' 으로 나왔다.** 이제 `spans` 로 판정하고 경과시간을 옆에 적는다:

- 주기 슬롯 구간 → `18ms` (회색)
- 기동 스냅샷 구간 → `4분` (호박색, `tr.aged`)
- 한 번도 안 읽음 → `미판독` (회색 행) — 거기 보이는 0 은 값이 아니라 섀도 초기값

**셋이 화면에서 구분된다.** 이것이 U8 을 만든 이유이고, 여기서 처음 눈에 보인다.

`unionSize`/`inFresh` 는 지웠다 — `spans` 는 겹치지 않게 이미 쪼개져 오므로 합집합을 셀
이유가 없다. 안 쓰는 채로 두면 다음 사람이 어느 쪽이 진짜인지 묻게 된다.
