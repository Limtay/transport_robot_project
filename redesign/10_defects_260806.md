### A1 — project 의 cmd_vel 이 엉뚱한 주소로 나갔다 ⚠ 치명

`TaskConfig_t::start_addr` 은 **inst 마다 의미가 다르다**: READ 는 `seg[0]` 의 사본(로그용),
**RW 는 write 구간**이다. 표 굽기가 READ 관례를 RW 에도 적용해서, `frames::kProject` 의
ECU RW 5칸이 cmd_vel 을 `180:8` 이 아니라 **`16:17`(SYS — 읽기 전용)** 에 쓰려 했다.

- **왜 안 드러났나**: 굽기가 생성자 안의 람다였고 결과가 private 이라 **어떤 테스트도
  그 변환을 지나가지 않았다.** 골든 테스트는 `TaskConfig_t` 를 손으로 만들어 쓴다.
  표(`test_slot_table`)와 wire(`test_golden_wire`) 사이 한 칸이 통째로 미검증.
- **수정**: 굽기를 `BakeFrame()`(`rd_slot_table.hpp`)으로 빼고 `test_frame_bake` 신설.
  **구 규칙을 되살려 실패를 먼저 확인**했다 (tick 1·3·5·7·9 전부).

### A5 — jeongae 대기 상한이 30초가 아니라 **0.75초**였다

`kWaitTicksMax = 150` 옆에 *"5Hz tick 기준 30초"*. **둘 다 틀렸다** —
`TickAutoSequence()` 호출부(`rd_schedule.cpp:658`)에 **레이트 분주가 없어** 200Hz 매 tick 마다
불린다 → 150 × 5ms ≈ 0.75초. **DPC 가 정상이어도 0.75초 안에 안 끝나는 전개는 무조건 Abort.**

- **왜 안 드러났나**: `wait_ticks > max` 는 어느 주기에서든 참이고 로그엔 "대기 초과" 만
  남는다. **U12 가 `wait_ticks` 를 `GET_STATUS` 로 꺼내 화면에 숫자를 띄우고 나서야 보였다.**
- **1차 수정** (사용자 결정 A): `kTickHz(200) × kWaitTimeoutS(10) = 2000`.
  실측 확인 — `wait_ticks` 가 ~200/s 로 오르고 **정확히 t=10.0s 에 만료**.
  `test_seq_tick_rate` 신설(소스를 읽어 분주 유무를 본다), **구 코드에 대고 실패 확인**.

- **⚠ 2차 수정 (2026-08-07): 10초 → 60초.** 값을 잘못 잡았던 이유가 **의미의 오해**였다.

  이 상한은 **"국면"당**이지 **"DPC 상태"당**이 아니다. `wait_ticks_` 는 브리지 단계에
  진입할 때 리셋되고, 대기 중 DPC 가 중간 상태를 밟는 것으로는 **리셋되지 않는다**
  (`WaitDpcStateLocked` 는 목표 도달 시에만 0 으로 되돌린다). 그런데 브리지의
  `DPC_WAIT_CAMERA` **하나**가 DPC 의 `2→3→4→5` **전 구간**을 덮는다.

  | 브리지 단계 | 덮는 DPC 구간 | 상한 |
  |---|---|---|
  | `DPC_WAIT_CAMERA` | `INIT(2)→DESCEND_1→DESCEND_2→WAIT(5)` **전체** | 60초 |
  | `DPC_WAIT_RETRACT` | `ASCEND_1(6)→ASCEND_2→FINISH(8)` **전체** | 60초 |

  **실제 전개 동작은 ≈40초** (사용자 실측). 10초로는 **정상 전개가 무조건 실패**한다 —
  스텁(3초 × 3단계 = 9초)으로는 아슬아슬하게 통과해서 **테스트가 진짜 문제를 가렸다.**
  → `kWaitTimeoutS = 60` (여유 20초). `rd_sequence.hpp` 주석에 "국면당" 을 못박았다.

> (패널 SW 이벤트에서만 바꾼다) 스텁이 STATE 를 단독으로 몰 수 있다.

## D. 의도적 설계 · 제약 (결함 아님 — 기록용)

### D1 — 모터가 없으면 ECU 는 AUTO 에서 `ESTOP_SW` 로 간다

복귀 조건이 `!motor_fault && health < WARN`(`ECU_V3/rd_system.c:457`) 이라 **모터가 CAN 에
붙어야** 한다. *"모터 부재 시 AUTO 주행 금지"* 라는 설계대로의 동작이다.

### D2 — `ControlFeedback.cmd` 의 의미가 프리셋에 따라 다르다

리드백 20B 를 뺀 뒤 `cmd` 는 *"브리지가 보낸 값"* 이 됐다. 다만 `control_test`
(auto_mode:none)에서는 `{164,16}` 리드백이 살아 있어 **거기서는 여전히 ECU 실값**이다.

### D3 — `OP_SET_CTR_MODE` 는 더 이상 검증하지 않는다

리드백이 없으면 브리지가 자기가 쓴 값을 다시 읽는 꼴이라 **무조건 통과**한다.
통과하는 검증은 거짓 보증이므로 루프를 제거하고 응답에 **"미검증"** 을 명시했다.

### D4 — DPC 의 미사용 레지스터와 부트 미러링 *(2026-08-07 사용자 확인)*

- **120·122·128~142 는 쓰지 않는다.** 소비자가 없는 것이 결함이 아니라 **설계대로**다.
- **DPC-A/B 부트는 미러링**이다 — `A_EN_BOOT`·`B_EN_BOOT` 가 같은 값에서 나오는 것이 의도.
  현재는 123 하나가 양쪽을 몰고, **121 을 123 과 미러링하도록 정리 예정**(C2b).

→ 브리지·웹은 이 주소들에 **쓰지 않아야** 한다. 화면 조치는 A13.

### D5 — MANUAL 에서 `sys_state` 가 목표값을 그대로 비춘다 *(의도적 설계)*

`sys_state`(57)는 `DPC_CTL.STATE` 를 복사해 발행하는데 전개 FSM 은 **`MODE == AUTO` 일 때만
돈다**(`rd_control.c:111`). 그래서 MANUAL 에서 127 에 2 를 쓰면 `sys_state` 가 2 로 읽히는데
아무것도 안 움직인다. **관측값이 정상 진행과 완전히 같아 증상만으로는 원인을 알 수 없다.**

**사용자 판정: 의도적 설계.** → 브리지가 `DPC_SET_AUTO` 단계(U5)로 **AUTO 를 먼저 보장**하는
것이 정식 대응이고, 이미 그렇게 되어 있다. 이 함정은 `rd_sequence.hpp` 주석에 남긴다.

### D6 — `DPC_CTL.STATE` 무검증 대입 *(의도적 설계)*

```c
DPC_CTL.STATE = reg.cmd_dpcb.sys_state_target;   // 마스크·검증 없음
```

**사용자 판정: 의도적 설계 — 사용자 의도를 그대로 반영한다.**

→ 따라서 **Orin 쪽 가드가 유일하고 정당한 방어선**이다. 브리지는
`dpc::IsWritableTarget()`(CTRL/HOLD/INIT/ASCEND_1)로 막고, **커맨드 경로(`dpc_set_seq`)와
시퀀스 경로가 같은 함수를 쓴다** — 두 경로가 다른 값을 허용하면 한쪽으로만 사고가 난다.
웹도 같은 목록을 들고 있고 `test_writable_seq_targets_match_the_firmware_gate` 가
펌웨어 헤더와 대조한다.

**이 가드는 지우면 안 된다.** 펌웨어가 검증하지 않기로 한 이상, 이것이 전부다.
